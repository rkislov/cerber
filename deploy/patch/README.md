# Управляемая установка обновлений

Это opt-in: установка выключена без ключа сервера и отдельно настроенного исполнителя.
Сетевой агент сохраняет прежнюю ограниченную учётную запись. Исполнитель не имеет токена
SIEM и не слушает сеть: он принимает из локального inbox только задания с подписью Ed25519,
проверяет привязку к узлу, срок запуска, точный список обновлений и запрет перезагрузки.
Результаты и отметка начала сохраняются в отдельной защищённой SQLite исполнителя.

Поддерживаются Windows x86_64 (WUA и настроенный в системе источник, включая WSUS),
Linux x86_64/aarch64 с APT/dpkg и DNF 4 с Python-модулем `dnf` в `/usr/bin/python3`.
Для Astra с APT и РЕД ОС с DNF применяются те же адаптеры; проверка конкретного выпуска
на изолированном стенде обязательна. APT-RPM, старый YUM и DNF5 сейчас отклоняются;
наличие read-only инвентаризации этих менеджеров не означает поддержки установки.
Сторонние MSI/EXE, winget, Store и произвольные скрипты не исполняются.

## Сервер

```sh
cerber patch keygen -out /secure/cerber-patch-signing.json
cerber -db /var/lib/cerber/siem.db siem serve -admin \
  -patch-key /secure/cerber-patch-signing.json
```

Для сетевого доступа добавьте существующие параметры TLS. Приватный ключ — только
на сервере (0600 на Unix, закрытая ACL в Windows); на узлы передаётся исключительно
файл `.pub`. Это отдельный ключ, не ключ базы знаний. Его замена требует обновления
публичного ключа исполнителей. Настройте именного администратора: общий bootstrap-ключ
и роли operator/analyst/viewer не могут создавать задания установки.

## Linux

Используйте существующую группу `cerber`, бинарник root:root без права записи агентом
в `/opt/cerber/cerber`. Отдельные каталоги не должны находиться внутри доступной агенту
для записи `/var/lib/cerber`.

```sh
sudo install -d -o root -g cerber -m 0750 /etc/cerber-patch /var/lib/cerber-patch
sudo install -d -o root -g cerber -m 0770 /var/lib/cerber-patch/inbox
sudo install -d -o root -g cerber -m 0750 /var/lib/cerber-patch/outbox
sudo install -d -o root -g root -m 0700 /var/lib/cerber-patch/private
sudo install -o root -g root -m 0644 signing.json.pub /etc/cerber-patch/signing.pub
```

Скопируйте `executor.linux.example.json` в `/etc/cerber-patch/executor.json` (root:root,
0644), укажите **серверный ID агента** и менеджер `apt` или `dnf`. Конфиг, ключ, outbox,
приватная БД и их родительские каталоги должны принадлежать root и быть недоступны
агенту для записи. Исполнитель проверяет права и отказывается запускаться при нарушении.
Запустите отдельную службу из `cerber-patch-executor.service`.

В конфиг сетевого агента добавьте:

```json
{"patch_inbox":"/var/lib/cerber-patch/inbox","patch_outbox":"/var/lib/cerber-patch/outbox"}
```

Для существующей systemd-службы агента добавьте drop-in:

```ini
[Service]
ReadWritePaths=/var/lib/cerber-patch/inbox
```

Затем перечитайте конфигурацию systemd и перезапустите обе службы. Исполнитель работает
в группе `cerber`, поэтому его результаты 0640 доступны агенту для чтения. Inbox очищается
после сохранения результата; outbox и журнал сохраняются для повторной доставки.

Команды установки запускаются через systemd в отдельных временных службах: запрещены
системные вызовы перезагрузки и доступ к сокетам systemd/D-Bus и sysrq. Изоляцию нельзя
отключить параметром задания. Это также может помешать пакетным скриптам управлять
службами — такие результаты необходимо проверить вручную. При отмене процесса ожидающего
исполнителя временная служба может продолжать работу до своего лимита 90 минут;
не повторяйте установку по одному лишь отсутствию результата.

APT сначала проверяет план без дополнительных установок/удалений, скачивает архивы
в приватный каталог, проверяет имя/версию/архитектуру и передаёт `dpkg` только выбранные
архивы. DNF проверяет точный набор транзакции и подписи пакетов; ключи автоматически
не импортируются. Новые зависимости требуют отдельного согласования и пока отклоняются.

## Windows

Сначала установите обычный `CerberAgent` под LocalService по инструкции `deploy/windows`.
В повышенной PowerShell:

```powershell
.\deploy\patch\Install-CerberPatchExecutor.ps1 -Binary .\bin\cerber.exe `
  -PublicKey .\signing.json.pub -AgentID SERVER_AGENT_ID
```

Установщик создаёт отдельное задание планировщика `CerberPatchExecutor` под SYSTEM,
но не запускает его. Каталоги `ProgramData\CerberPatch` и `Program Files\CerberPatch`
отделены от изменяемых агентом данных. Только SYSTEM и Administrators могут изменять
исполнитель, конфиг, публичный ключ, outbox и журнал. SID службы `CerberAgent` может
писать только в inbox и читать outbox. Исполнитель проверяет владельца и DACL своих файлов.
Установка в существующие каталоги отклоняется, чтобы не уничтожить журнал.

Добавьте в конфиг агента:

```json
{"patch_inbox":"C:\\ProgramData\\CerberPatch\\inbox","patch_outbox":"C:\\ProgramData\\CerberPatch\\outbox"}
```

```powershell
Start-ScheduledTask -TaskName CerberPatchExecutor
Restart-Service CerberAgent
Get-ScheduledTaskInfo -TaskName CerberPatchExecutor
```

WUA повторно ищет выбранные UpdateID/revision в настроенной службе. Обновления с
непринятым EULA или требующие интерактивного ввода отклоняются: Cerber не принимает
лицензионные соглашения. Коды WUA/HRESULT и требование перезагрузки сохраняются.
Cerber не вызывает перезагрузку и не меняет политики Windows Update. Существующие
независимые политики автоматической перезагрузки ОС должны быть согласованы администратором
до пилотной эксплуатации ([политики Microsoft](https://learn.microsoft.com/en-us/windows/deployment/update/waas-restart)).

## Работа администратора

Откройте карточку агента → «Установка обновлений». Выберите до 20 обновлений из свежего
снимка (до 24 часов) → «Проверить установку на агенте». После успешной проверки (до 15 минут
с момента её создания) отметьте подтверждение и нажмите «Установить ... без перезагрузки».
Список и версии фиксируются сервером, данные из браузера не задают команды или пути.
Проверка используется для установки один раз. При смене снимка требуется новая проверка.

В истории видны очередь/выполнение, результат каждого обновления и необходимость
перезагрузки: «требуется», «не требуется по данным Windows» или «неизвестно».
Отсутствие Linux-файла `reboot-required` не доказывает, что перезагрузка не нужна;
установка ядра помечается как требующая перезагрузки. Перезагрузку выполняет администратор.
После установки запустите штатную инвентаризацию/проверку обновлений для обновления
снимка на сервере; локальная проверка результата не заменяет доставку нового инвентаря.

Отменить можно только ожидающее задание. Начатая установка после сбоя не повторяется:
показывается `unknown` с необходимостью сверить WUA/DNF/dpkg и состояние пакетов.
Автоматического отката и восстановления установки после обрыва нет. Не удаляйте журнал
исполнителя для «повторного запуска». Групповые волны и расписания установки пока отсутствуют.

До включения в рабочей сети проверьте установку и сбои на изолированных Windows/Linux
машинах. Автотесты используют фикстуры и временный корень dpkg; они не устанавливают
обновления на рабочую ОС разработчика и не подтверждают совместимость со всеми выпусками ОС.
