# Сервер за TLS-прокси

Соберите статический Linux-бинарник под архитектуру узла. В приватном build-context
нужны Dockerfile, `cerber` и системный `ca-certificates.crt`. Образ не содержит секретов.
До сборки задайте бинарнику режим 0755, сертификатам CA — 0644.
Создайте приватный каталог состояния с владельцем UID/GID службы (в примере 1000).
Именного администратора создайте CLI `siem user-add` до публикации интерфейса;
случайный начальный пароль храните отдельно с режимом 0600.

Пример запуска (конкретные пути, UID и лимиты выбирает оператор):

```sh
docker run -d --name cerber-siem --restart unless-stopped \
  --network host --user 1000:1000 --read-only --cap-drop ALL --security-opt no-new-privileges \
  --pids-limit 128 --memory 768m --cpus 1 \
  --log-opt max-size=20m --log-opt max-file=3 \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  -v /srv/cerber/state:/state \
  cerber-siem:VERSION -db /state/control.db siem serve \
  -admin -admin-secure-cookies -listen 127.0.0.1:18790 \
  -events-db /state/events.db -event-archive-dir /state/archives
```

Проксируйте выделенное DNS-имя на `127.0.0.1:18790` с сохранением Host и действительным
TLS-сертификатом. Backend не публикуйте вне loopback. До изменения шлюза сохраните
конфигурацию, проверьте синтаксис и используйте штатный reload.
Проверьте HTTPS, 401 для API без авторизации, вход, Secure-cookie, доступ агентов и
восстановление после перезапуска. Хранение/архивирование по умолчанию выключено;
не включайте удаление без утверждённой политики. Патч-исполнители отдельно opt-in.

Перед обновлением сохраните согласованную резервную копию обеих SQLite БД и архивов
при остановленной службе; не копируйте только основной файл живой WAL-БД.
Предыдущий образ и конфигурацию храните до проверки. Откат бинарника через миграцию
схемы не гарантируется — восстанавливайте согласованный комплект резервной копии.

## Контроль доставки и архивов

В обзоре доступны средние скорости приёма/нормализации за интервал, количество
ожидающих событий, возраст старейшего ожидающего события, учтённый объём журнала
и его лимит. Отдельно показано свободное место раздела; размер SQLite и архивов
не равен учтённому объёму исходных событий и квитанций. Очереди агентов агрегируются
для текущей страницы; устаревшая телеметрия не выдаётся за пустую очередь.

Агентские предупреждения сохраняются в основной БД: отсутствие подтверждений при
непустой очереди пять минут, рост очереди за период наблюдения либо половина её
лимита, устаревшая телеметрия сборщика при свежем heartbeat. Тихий источник без
очереди не считается отказом. Восстановление автоматически закрывает условие;
подтверждение оператором его не устраняет. Наблюдение за очередью переживает рестарт.

Монитор конвейера проверяется каждые 30 секунд: задержка от пяти минут, заполнение
журнала 80/95%, свободное место менее 10/5% (менее 1 ГиБ — критическое), ошибки
архивирования. Изменения состояния поступают в устойчивую очередь SMTP отдельно
от корреляций, включая восстановление; доставка требует включённого SMTP и
получателей в настройках. Это не канал аварийного оповещения при полной потере БД
или процесса SIEM — для этого необходим внешний мониторинг.

В «Хранение и архивы» задаются срок оперативного хранения, срок архивов (0 означает
бессрочно) и лимит журнала в МиБ. Старые API-клиенты, не передающие `max_bytes`,
сохраняют текущий лимит; по умолчанию он равен 1 ГиБ. Лимит нельзя уменьшить ниже
уже учтённого объёма. Перенос выполняется только после обработки и проверки файла;
доказательства срабатываний остаются в оперативном журнале. Поэтому срок — порог
допуска к архивированию, а не гарантия удаления каждой записи к указанной дате.

Кнопка проверки архива проверяет SHA-256, gzip до конца, число и последовательности
записей; исходник открывается из архива без повторной корреляции. Истёкший или
повреждённый архив не возвращается как восстановленный. JSONL.gz и БД с индексом
архивов должны резервироваться согласованно. Миграции: control schema 12,
events schema 5; возврат к старому бинарнику требует согласованного восстановления
резервной копии, а не запуска старой версии на новой схеме.

## Физическая ёмкость

В политике отдельно задайте бюджет SQLite вместе с WAL/SHM, бюджет архивного
каталога и минимальное свободное место на каждом разделе. Значения по умолчанию:
16 ГиБ, 8 ГиБ и 2 ГиБ. Это защита записей Cerber, а не квота файловой системы:
оставляйте запас под ОС, другие приложения и резервные копии. Ограничение журнала
учитывает исходники, но не индексы, нормализованные события и служебные таблицы.

При нехватке места новые пакеты получают HTTP 503 и остаются в очередях агентов.
Очереди конечны: устраните причину до их заполнения. Уже подтверждённые повторы
получают прежнюю квитанцию. Обработка и архивирование продолжаются при наличии
аварийного рабочего резерва; checkpoint освобождает WAL без удаления файлов вручную.
Освобождённые страницы SQLite используются повторно; полный VACUUM автоматически
не запускается, поскольку требует дополнительного места.

Для растущей установки вынесите `-events-db` и `-event-archive-dir` на подготовленные
тома, например `/events/events.db` и `/archives`, добавив отдельные bind mounts с
владельцем UID/GID службы. Переносите согласованный комплект при остановленном SIEM,
проверьте доступность архивов после переноса. Разные каталоги на одном разделе не
создают независимую ёмкость. Бессрочные архивы требуют увеличения хранилища по мере
роста; достижение бюджета не удаляет их и не сокращает утверждённые сроки.
