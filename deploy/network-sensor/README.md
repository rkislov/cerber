# Отдельный сетевой сенсор

`cerber-sensor` — самостоятельный компонент на Go для пассивного сбора.
Он имеет собственную регистрацию, процесс, конфигурацию и очередь SQLite.
Он не исполняет команды агента, не устанавливает обновления, не меняет правила
межсетевого экрана и не запускает active response. Suricata работает отдельной
службой с собственными правилами и правами захвата; этот компонент принимает EVE.
Активное сканирование подсетей остаётся задачей назначенного агента.

## Входы

- Syslog RFC5424 и RFC3164: UDP, TCP (newline / RFC6587 octet-counting), TLS с
  проверкой клиентского сертификата. Неизвестные сообщения остаются общими
  событиями сетевого устройства. Фирменные шаблоны не угадываются.
- CEF: явно выбранный формат `cef-firewall` или `cef-fess` внутри Syslog.
  Действуют ограничения имеющегося CEF-адаптера, включая обязательный `rt` RFC3339.
- NetFlow **v5**, IPv4, UDP: адреса, порты, протокол, интервалы, интерфейсы,
  счётчики пакетов/байтов и исходные параметры sampling. Счётчики не умножаются
  автоматически на sampling interval. Это метаданные, а не содержимое пакетов.
- Suricata EVE JSON: файл JSONL либо TCP/TLS JSONL. Сохраняются исходная запись,
  flow_id без потери точности, адреса/порты, интервалы потока и сигнатура alert.
  Наличие IDS-сигнала не объявляется успешной атакой или фактом блокировки.

- NetFlow **v9** и **IPFIX (v10)** по UDP: обычные и Options-шаблоны, IPv4/IPv6,
  целочисленные счётчики уменьшенной длины, поля IPFIX переменной длины и
  enterprise-поля. Неизвестные поля сохраняются в исходнике без угадывания смысла.
  Options records сохраняются как метаданные: их scope не становится IP участника,
  а sampling из Options не распространяется автоматически на потоки.

sFlow, SNMP traps и IPFIX через TCP/SCTP/DTLS пока не поддерживаются.
Декодер v9/IPFIX — отдельный пакет `internal/flowexport`, без зависимостей от
хранилища и сервера. Исходник каждого потока содержит заголовок экспорта,
точный снимок шаблона и байты записи; сервер повторно разбирает его независимо
от текущего кеша сенсора.

## Установка

Соберите `go build -trimpath -o cerber-sensor ./cmd/cerber-sensor` (Linux amd64
или arm64). Создайте непривилегированного пользователя `cerber-sensor`, разместите
бинарный файл в `/opt/cerber-sensor/`, конфигурацию в `/etc/cerber-sensor/`.
Для сетевых входов выше 1024 root/capabilities не нужны. Выпустите отдельную
регистрацию сенсора на активе его узла и реквизиты через существующий `siem enroll -asset ID
-out FILE`; файл с токеном храните с правами 0600. Не используйте реквизиты другого
агента. Пример конфигурации — `sensor.example.json`; unit — `cerber-sensor.service`.

`cerber-sensor -config /etc/cerber-sensor/sensor.json -check` проверяет структуру
конфигурации. Обычный запуск также проверяет реквизиты и TLS-файлы и привязывает
все порты до начала работы. Доставка в SIEM требует HTTPS; HTTP допустим только
на literal loopback. Для чтения EVE дайте пользователю доступ только на чтение
конкретного файла/каталога, а не административные права.

В примере все сокеты слушают loopback. Для оборудования укажите адрес интерфейса
управления и точные CIDR отправителей в `allow`. Для TLS задайте `protocol: tls`,
`cert`, `key`, `client_ca` (абсолютные пути). Для удалённого plain TCP необходимо
явно установить `allow_plain_remote: true`. UDP не аутентифицирует отправителя;
используйте изолированную сеть/VPN и сетевые ACL. Allowlist — не замена TLS.
Компонент сам не открывает порты в firewall и не настраивает устройства.

Для Suricata настройте копирование трафика через SPAN/TAP на отдельный интерфейс
сенсора и её вывод EVE. На сервере SIEM захват автоматически не включается.
Права захвата нужны движку Suricata, а не приёмнику Cerber. Одного NetFlow
недостаточно для анализа содержимого HTTP/DNS/TLS или сигнатурного DPI.

## Надёжность и ограничения

Очередь сохраняет исходные записи до проверенной квитанции SIEM; повтор после
потери квитанции идемпотентен. Лимиты: 1000 пакетов доставки / 256 МиБ полезных
данных, до 100 записей в пакете; SQLite/WAL требуют дополнительного места.
UDP v5 содержит до 30 записей. Для TCP/UDP текст ограничен 12 КБ и общим лимитом
JSON события 16 КиБ. На вход — до 32 TCP-соединений, тайм-аут чтения 30 секунд.
Это начальный приёмник для небольших установок, не система захвата line rate.

При заполнении очереди TCP-подключение закрывается; **TCP не даёт прикладной
квитанции о сохранении**. UDP может теряться при перегрузке, в сети и в ядре;
датаграммы, отвергнутые приложением, отражаются в счётчиках процесса.
Счётчики `received/stored_records/rejected` выводятся раз в минуту и сбрасываются
при перезапуске; они относятся к сокетным входам, не измеряют потери в сети/ядре.
Очередь и ошибки доставки передаются стандартным heartbeat в SIEM.
У сенсора нет инвентаризации ОС: новый heartbeat помечает её неприменимой,
а карточка в общем списке ведёт в отдельный раздел сенсоров. Предупреждение
об отсутствии инвентаря для такого сенсора не создаётся; контроль связи и
очереди событий продолжает работать.

EVE-файл читается с атомарным курсором; незавершённая строка остаётся до дописывания.
Замена/усечение файла останавливает чтение без сброса курсора. Пока нет автоматической
ротации: сначала дренируйте файл и очередь, остановите сенсор, сохраните старый
файл и БД, укажите новый файл и новую БД очереди. Не удаляйте очередь с недоставленными
событиями. Для постоянно ротируемых журналов предпочтителен внешний надёжный
forwarder с JSONL TCP/TLS. Ошибки чтения видны в heartbeat; файловый режим не
предназначен для неограниченного роста EVE. Настройте лимиты диска у Suricata/forwarder.

## События, IOC и граф

В админке доступны источники Syslog/NetFlow/Suricata и классы «Сетевые устройства»,
«Сетевые потоки», «Сигналы IDS». Исходная запись доступна стандартной кнопкой.
Устройство-отправитель, заявленное имя из Syslog и адреса участников разделены.
RFC3164 не задаёт год/часовой пояс: используется время приёма, исходная дата сохранена.
NetFlow с неоднозначным интервалом более 24 часов или невозможной датой отклоняется.

Структурированные IP проходят существующие правила ThreatFox и их группы/исключения.
CEF использует существующие правила МСЭ/FESS. Общий Syslog не превращается в
авторизацию по ключевым словам. Suricata alert сохраняется как IDS-событие;
отдельные настраиваемые корреляционные правила по сигнатурам — следующий этап.
Срабатывания сетевого сенсора помечены `observer_only`: они не создают предложений
active response на наблюдателе.

В графе инцидента к включённым соединениям WFP добавляется подтверждающее
наблюдение TCP с точно совпавшими адресами/портами и временем внутри интервала
±5 секунд. До 100 кандидатов / 512 КиБ на соединение, окно поиска 30 минут,
общий предел 20 шагов цепочки. Группы и исключения текущего правила применяются
также к сенсору; добавьте его в нужную группу для разрешённого контекста.
Сенсор показан как наблюдатель, без выдуманных SID/сеансов/PID. NAT не угадывается,
IP сам по себе не объединяет активы; sampling, часы и повторные порты ограничивают
вывод. Контекст только читается, не создаёт оповещений или правил блокировки.

Форматы: [Syslog RFC5424](https://www.rfc-editor.org/rfc/rfc5424),
[TCP framing RFC6587](https://www.rfc-editor.org/rfc/rfc6587),
[NetFlow v5](https://www.cisco.com/c/en/us/td/docs/net_mgmt/netflow_collection_engine/5-0-3/user/guide/format.html),
[Suricata EVE](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html).

## NetFlow v9 / IPFIX

Для входа задайте `format: netflow9` или `format: ipfix`, `protocol: udp`, адрес
прослушивания и allowlist экспортёров. Версия должна соответствовать входу.
Примеры добавлены в `sensor.example.json`. IPFIX и v9 используют общий источник
`network:netflow`; конкретный формат виден в продукте события и в графе.

Ключ кеша: вход + IP/UDP-порт отправителя + версия + Source ID/Observation Domain.
Одинаковый Template ID на разных устройствах/доменах не объединяется. До 64 таких
сеансов, 64 шаблонов на сеанс, 64 полей в шаблоне, 100 записей в датаграмме;
датаграмма до 12 КБ, запись до 8 КиБ. При превышении лимита пакет отклоняется.
TTL шаблона — 900 секунд, `template_ttl_seconds` позволяет задать 60–86400.
Настройте TTL не меньше трёх интервалов обновления шаблонов экспортёра.
Данные не продлевают жизнь шаблона. Неактивные сеансы также истекают по TTL.

Перезапуск сенсора очищает кеш, но не очередь: сохранённые потоки имеют собственные
снимки шаблонов. Неизвестные/истёкшие Data Sets не буферизуются и не декодируются
старым шаблоном; счётчик `unknown_sets` и heartbeat показывают проблему. После
получения шаблона принимаются последующие записи, потерянные задним числом не
восстанавливаются. На устройстве требуется периодическое обновление шаблонов.

Откат sequence при более новом времени экспорта и падение v9 uptime сбрасывают
кеш сеанса; естественное переполнение счётчиков учитывается. Старые/переставленные
датаграммы отклоняются. При откате часов экспортёра приём требует истечения TTL
или новой транспортной сессии. Невозможно надёжно определить любой перезапуск
по UDP без сигнала экспортёра; последовательность — защитная эвристика.
Структурно повреждённая датаграмма сбрасывает шаблоны своего сеанса. Изменённый
Template ID заменяется новым шаблоном. IPFIX withdrawals по UDP игнорируются
согласно RFC7011, срок шаблонов контролируется TTL. Счётчики `templates`,
`unknown_sets`, `ignored_udp_withdrawals`, `resets`, `stale_packets` выводятся
ежеминутно, сбрасываются при перезапуске и не являются оценкой всех потерь UDP.

Нормализуются стандартные IE: адреса 8/12/27/28, порты 7/11, протокол 4,
интерфейсы 10/14, delta-счётчики 1/2, sampling 34/35 непосредственно в записи.
Время: v9 FIRST/LAST_SWITCHED 22/21; IPFIX 150–157 (seconds, milliseconds,
NTP micro/nanoseconds), 158/159 (delta microseconds), 22/21 вместе с 160
(systemInitTimeMilliseconds). Для последнего варианта wrap uptime свыше 49 суток
не угадывается. Интервал до 24 часов; противоречащие часы/невозможные времена
отправляются в карантин. Неизвестные enterprise IE не заменяют стандартные.

Без полной пары поддерживаемых временных полей событие сохраняется со временем
экспорта, но **не участвует в сопоставлении с WFP**. Из одного exportTime нельзя
заключить, когда возникло соединение. Для графа по-прежнему нужны TCP tuple,
достоверный интервал с допуском ±5 секунд и разрешение текущей политики для
сенсора. В деталях видны домен, Template ID, sequence, SHA-256 шаблона и порт
экспортёра. UDP spoofing, NAT, sampling и перестановка пакетов ограничивают
доказательность; active response на наблюдателе остаётся выключенным.

Спецификации: [NetFlow v9 RFC3954](https://www.rfc-editor.org/rfc/rfc3954),
[IPFIX RFC7011](https://www.rfc-editor.org/rfc/rfc7011),
[стандартные Information Elements IANA](https://www.iana.org/assignments/ipfix).

## Управление и диагностика в админке

Раздел **«Сетевые сенсоры»** показывает отдельные регистрации сенсоров, в том числе
несколько сенсоров/агентов на одном активе. Сенсор появляется после первого
heartbeat новой версии. Свежесть определяется временем приёма на сервере;
последние известные данные остаются видимыми при потере связи и отзыве доступа.
Инвентаризация для сенсора не требуется; его очередь событий показана отдельно.

По каждому действующему входу видны формат, транспорт, адрес прослушивания,
allowlist, состояние, последнее сообщение, последняя ошибка и время ошибки.
Счётчики сообщений, байтов, сохранённых записей, сообщений с потерями, шаблонов,
неизвестных Data Sets, сбросов сессий и устаревших пакетов накоплены с запуска
процесса. Скорость усредняется за интервал между отчётами, обычно около минуты.
Историческая ошибка не означает текущий отказ: последующий успешный приём
восстанавливает состояние. Файловый вход сообщает состояние чтения без сетевых
счётчиков. Ошибка локальных Syslog/EVE listener или первичного запуска без
сохранённой политики останавливает компонент; причину смотрите в systemd/Docker
log. Если после перезапуска не удалось открыть входы сохранённой центральной
политики, сенсор продолжает heartbeat и доставку очереди, сообщает ошибку и ID
входа. Исправьте или удалите его в админке: сенсор сможет применить новую версию.

Для NetFlow/IPFIX отображаются до **8 последних сеансов экспортёров на вход**:
IP, UDP-порт, Source ID/Observation Domain, время и счётчики. При вытеснении
старейшего сеанса его индивидуальные счётчики теряются, общие остаются.
Это ограниченный список наблюдений, не реестр уникальных доверенных устройств.
Отвергнутые allowlist пакеты не заполняют этот список. Неизвестный набор считается
сообщением с потерями даже при успешном сохранении других записей пакета.
Ошибки обрамления/ограничения соединений входят в отказы текстовых входов.
Байты слишком длинной UDP-датаграммы видны только до границы приёмного буфера;
потери в сети/ядре не измеряются. Серверный карантин нормализации смотрите
в журнале событий, а не в счётчике разбора на сенсоре.

Именованный **администратор** в карточке сенсора может:

- создать NetFlow v5/v9/IPFIX вход с уникальным ID, IPv4/IPv6-адресом и UDP-портом;
- изменить адрес, порт и формат существующего входа;
- удалить вход с подтверждением: сокет закрывается, очередь сохраняется;
- включить/приостановить приём, сохранив доставку уже записанной очереди;
- заменить список разрешённых экспортёров (1–128 IP или канонических CIDR без
  повторов; одиночные IP форма сохраняет как /32 или /128);
- изменить TTL шаблонов v9/IPFIX (60–86400 секунд);
- вернуть локальному входу настройки `sensor.json` или восстановить его после
  удаления. Центральный вход восстанавливается повторным созданием.

Нужна обновлённая версия `cerber-sensor`, сообщающая `input_management: 1`.
Для старого сенсора доступны прежние пауза/allowlist/TTL, новые поля сервер
отклоняет. После обновления дождитесь heartbeat. Допускается начальный
`"inputs": []` в `sensor.json`: все NetFlow/IPFIX-входы затем создаются из админки.
Всего допускается 8 действующих входов, включая локальные Syslog/EVE и входы на
паузе. Политика вмещает до 16 записей (8 удалённых локальных и 8 новых).

Остальные роли только просматривают раздел. POST защищён сессией, Origin и CSRF;
роль повторно проверяется в транзакции. Сохранение требует текущую ревизию;
конфликт не перетирает чужую правку. Изменение журналируется с автором, старой и
новой конфигурацией (`sensor.policy_changed`). Форма не перезаписывается фоновым
обновлением. Экран различает желаемую и применённую версии.

Политика доставляется только в ответ на авторизованный heartbeat конкретного
сенсора. Применение занимает до двух обменов (получение и подтверждение).
Сначала сенсор открывает все новые UDP-сокеты, затем атомарно сохраняет политику в файл
`<spool>.sensor-policy.json` (0600; на Linux также fsync каталога). Сохранённая
конфигурация действует после перезапуска без доступного SIEM. При занятом порте,
недоступном адресе, недостаточных правах или ошибке записи действующая
конфигурация остаётся прежней, сервер видит ошибку применения. Новые неподтверждённые
входы можно исправить или удалить в блоке сохранённой конфигурации.
Изменённый вход теряет кеш шаблонов, соседние входы и сохранённая очередь
сохраняются. Новые данные ждут повторной отправки шаблонов экспортёром.

Адрес должен принадлежать сенсору. `0.0.0.0` и `::` слушают все интерфейсы своей
семьи; IPv6-сокеты работают только с IPv6. Используются буквальные адреса без
DNS и zone ID, UDP-порты 1–65535. Совпадающие/перекрывающиеся UDP-входы
отклоняются. Переход между конкретным адресом и wildcard на том же порте требует
удаления входа с ожиданием подтверждения, затем создания: одновременно открыть
оба сокета нельзя. Для портов ниже 1024 могут потребоваться права ОС.

TLS-файлы, пути EVE, Syslog-входы и реквизиты SIEM настраиваются локально.
Центральная политика не меняет firewall и `sensor.json`; удаление локального
NetFlow/IPFIX-входа сохраняется как переопределение. Кеш привязан к ID регистрации
и хешу локального списка
входов. Перед изменением локального списка остановите сенсор и согласуйте
политику с ним: сохраните резервную копию файла политики, сбросьте центральные
переопределения, затем перенесите старый кеш из рабочего пути. При несовпадении
отпечатка сенсор не запускает входы молча с иными настройками.
Статус heartbeat ограничен 128 КиБ, ответ политики — 64 КиБ; максимум 8 входов.

### История и автоматические оповещения

В карточке сенсора доступны графики сообщений/с, КиБ/с, ошибок разбора и наборов
без шаблона, а также максимума очереди доставки. Историю можно смотреть целиком
или по входу, включая недавно удалённые входы. Агрегаты хранятся в основной БД:
поминутные — сутки, пятиминутные — неделю, часовые — 30 дней. Общий предел —
200 000 строк на сервер; при его достижении старейшие удаляются раньше срока.
Очистка выполняется при heartbeat и обходе оповещений, включая историю отключённых
сенсоров. Освобождённые страницы SQLite повторно используются.

Скорости вычисляются из приращений счётчиков двух последовательных heartbeat.
Повторный отчёт не учитывается дважды; перезапуск, уменьшение счётчика, разрыв
более пяти минут или недостоверные часы дают пропуск, а не всплеск или нулевую
скорость. Очередь относится ко всему сенсору; её график не показывается для
отдельного входа. Графики поддерживают наведение и стрелки клавиатуры.

Кнопка **«Настроить оповещения»** доступна именованному администратору после
обновления сенсора (`monitoring_version: 1`). Остальные роли читают историю.
Настройки сохраняются отдельно от входов, с проверкой ревизии и аудитом;
изменение входа также сохраняет настройки оповещений.

По умолчанию включены проверки отсутствия heartbeat и неприменённой конфигурации
после пяти минут, ошибок за пятиминутное окно (20% при минимум 20 сообщениях),
10 наборов без шаблона, заполнения очереди (500 пакетов или 128 МиБ), устойчивого
роста очереди и задержки подтверждения доставки. Пороги настраиваются.
Ошибки суммируются по завершённым минутам и проверяются отдельно для каждого
действующего входа. Заполнение очереди и явная ошибка применения настроек
проверяются при ближайшем обходе; один пакет после простоя не означает отказ.

Отсутствие трафика проверяется **только для явно заданных ожидаемых экспортёров**:
до 32 пар «вход + IP» с периодом тишины от 3 минут до 7 дней. Пустой IP означает
любой разрешённый источник этого входа. Указывайте адрес, разрешённый allowlist,
и период больше обычной паузы экспорта. Контакт учитывается независимо от
ограниченного списка последних восьми сеансов. Отклонённые allowlist пакеты
не подтверждают контакт; принятый, но неразобранный пакет подтверждает контакт,
а его ошибка учитывается отдельно. После запуска сенсора, включения наблюдения
или сохранения его настроек действует новый период ожидания. Приостановленные
и удалённые входы не проверяются; их старые ожидания можно удалить в форме.
UDP-адрес подтверждает наблюдение пакета, но не удостоверяет устройство.

Срабатывания попадают в «Предупреждения» и существующую очередь SMTP-уведомлений.
Открытое предупреждение не дублируется при каждом обходе; его данные обновляются,
после восстановления оно закрывается. Потеря связи или недостоверный статус не
считаются восстановлением зависимых проверок. Выключатель отключает оповещения
сенсора; история продолжает накапливаться. SMTP использует отдельные настройки
раздела «Настройки → SMTP».

### sFlow v5

Формат `sflow5` добавляет UDP-приём компактных/расширенных flow samples, записей
sampled IPv4/IPv6 и sampled header (Ethernet, до двух VLAN, IPv4/IPv6). Для IPv6
учитываются до восьми extension headers; не начальные фрагменты не получают
выдуманные TCP/UDP-порты. Неизвестные sample/record types и counter samples
сохраняются как исходные данные/метаданные, без трактовки их как соединений.
Одна запись события соответствует одной выборке. Поддерживаются до 100 samples
и 100 records/sample в датаграмме до 12 000 байт. Исходная датаграмма сохраняется
для повторной нормализации; экспортированные счётчики интерфейсов пока не разбираются.

Создать вход можно в админке после heartbeat с `sflow_version: 1`; обычный порт
6343, адрес и allowlist задаются явно. Параметр TTL шаблонов не применяется.
События используют `network:netflow`, профиль `sflow5` и класс `network_flow` при
распознанных IP. Адрес UDP-отправителя и заявленный адрес sFlow agent хранятся
раздельно, заявленный адрес не обходит allowlist. Счётчики отражают одну выборку,
не умножаются на sampling rate. В графе показаны выборочность и sampling rate;
связь по TCP tuple использует время приёма сенсором с прежним допуском 5 секунд.
Задержка экспорта неизвестна; принадлежность процессу/учётке этим не доказывается.
Основа декодера: [спецификация sFlow v5](https://sflow.org/sflow_version_5.txt).

### Ротация файлов Suricata EVE

Файловый вход EVE поддерживает rename-ротацию `eve.json` → `eve.json.1`, далее
`.2` … `.32`. Дочитываются поколения по порядку; курсор хранит идентификатор
файла ОС, смещение и отпечаток префикса. Переход выполняется после полного чтения
и двух секунд неизменности старого файла. Курсор продвигается только вместе с
записью пакета в durable spool; повторное чтение создаёт те же ID событий.
Старые курсоры LineFile распознаются по сохранённому префиксу.

Остановите запись в старое поколение штатным reopen Suricata перед продолжением
ротации. Старые файлы должны оставаться неизменными, несжатыми и доступными до
дочитывания; имя с датой, `copytruncate` и gzip-поколения не поддерживаются.
Потерянный файл, усечение или незавершённая последняя строка старого поколения
оставляют курсор на месте и отображаются как ошибка источника. При задержке
доставки сначала дождитесь дочитывания/освобождения очереди, затем удаляйте файлы.
Это обработка внешней ротации; сенсор не удаляет журналы Suricata самостоятельно.
