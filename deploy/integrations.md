# SMTP and ThreatFox settings

The named administrator console exposes **Настройки**. Operators, analysts, viewers and legacy bootstrap sessions cannot read or change integration settings. POST requests use the console's existing origin and CSRF checks.

Start the SIEM with both `-settings-file /state/integrations.json` and `-settings-key /run/integrations.key`. Create the key once from 32 cryptographically random bytes, restrict it to the service account (0600), and mount it read-only separately from state. Keep a protected backup of the key separately from encrypted state backups; losing it prevents decryption. No schema migration is required.

The settings file is encrypted and authenticated with AES-256-GCM and replaced atomically. The browser receives only secret-presence flags. Blank password/key inputs preserve saved secrets; explicit deletion is separate. Concurrent edits are rejected by version. The encrypted history records the last 1,000 changes, with actor, time and changed sections, without secret values.

SMTP supports verified TLS or mandatory STARTTLS and optional PLAIN authentication after TLS. The connection test does not submit MAIL, RCPT or DATA and sends no email. ThreatFox checks the saved Auth-Key against the fixed official API endpoint using the `types` query; redirects are rejected. Tests use saved settings, so save edits first. The feature provides settings and connectivity checks; automatic email notifications and IOC synchronization/matching are not enabled by this change.

The overview also exposes authenticated `/admin/api/system` snapshots, cached for five seconds. Linux reports process CPU (100% equals one CPU core), host load average, memory usage/limit for cgroups when available (otherwise host memory), and available disk space on the database volume. Other platforms report unavailable resource counters. Database probes read `PRAGMA user_version` with a one-second deadline; they check read availability, not integrity or write readiness. Sizes include a separate WAL measurement. Failed probes remain visible independently of the inventory overview.

## Automatic notifications and IOC correlation

SMTP and ThreatFox have separate save buttons and independent enable switches. Saving one section preserves the other section, including unsaved browser fields. Both use the shared version for concurrency protection.

The server opens a separate private SQLite runtime file next to encrypted settings (`SETTINGS_FILE.runtime.db`). Back it up with state. It stores the complete imported IOC snapshot, notification cursors, delivery queue and retry status; it contains no SMTP password or ThreatFox key. SMTP notifications cover unresolved agent warnings and open correlation detections. Existing retained open detections/warnings are eligible when notifications are first enabled. Delivery is limited to ten messages per 30-second cycle, retries use exponential backoff (up to about 17 hours), and stable Message-ID values help deduplication. Delivery is at least once: an SMTP acknowledgment followed by a local failure can cause a repeat. Queued messages use the currently saved recipients at send time. Disabling SMTP pauses delivery. The test button sends no mail; enabling notifications does.

The initial and every subsequent ThreatFox sync use the **full.csv.zip** export, never a seven-day `get_iocs` substitute. The official export URL requires the key in its path; the fixed HTTPS host, rejected redirects, generic errors and lack of request logging prevent URL secrets appearing in Cerber logs/API errors. The download is capped at 128 MiB compressed / 512 MiB uncompressed / one million indicators. Parsing errors, HTTP errors and empty exports preserve the previous snapshot. A successful import is atomic. Full refresh runs at startup, each hour, after saving ThreatFox, or via the manual full-sync button. Disabling pauses matching/sync; an in-flight authorized request can finish.

All current indicators (including file hashes) are retained; current event normalization supports matching IP, IP:port destination, domains in absolute request URLs, and exact URLs. Hash matching awaits normalized file-hash telemetry. IP matching supports IPv4 and IPv6. `threatfox.ioc_match` denotes an exact supported indicator match. `threatfox.ip_match` denotes only the IP portion of an ip:port indicator, with **medium** severity and an explicit unconfirmed-port warning. No response/blocking is performed. Event time must fall between first observation and last observation plus six months. ThreatFox itself excludes expired indicators older than six months.

IOC scans have a durable independent event cursor and process 200 records every two seconds. A changed feed rechecks retained normalized events from the beginning; archived events require a separate reprocessing workflow. Detection IDs are stable per event/IOC and replays do not duplicate detections. Evidence links reference the normalized event ID. Settings display IOC count, last successful full sync, synchronization errors, event-scan errors, queued and sent mail counts.

Overview IP counts include unique addresses of non-revoked agents; subnet counts are explicitly an estimate using IPv4 /24 and IPv6 /64, not discovered interface netmasks.
