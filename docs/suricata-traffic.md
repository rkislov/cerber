# Пассивный захват SPAN/TAP и граф инцидента

Suricata работает отдельным процессом или контейнером. `cerber-sensor` читает
локальный EVE, сохраняет записи в надёжной очереди и передаёт их в SIEM по
аутентифицированному каналу. Управление подписанными правилами описано в
[suricata-rules.md](suricata-rules.md).

## Подключение зеркального порта

На коммутаторе настройте SPAN в сторону выделенного интерфейса Linux-сенсора либо
подключите к нему выход TAP. Cerber не настраивает коммутатор. Интерфейс должен
быть поднят и не иметь назначенных адресов; управляющее соединение использует
другой интерфейс. Захват требует Linux, Suricata 7/8 и AF_PACKET. В этой поставке
поддерживается один интерфейс на движок. Режим пассивный, без NFQUEUE, IPS,
пересылки пакетов и изменений правил доступа.

В `deploy/suricata` есть Dockerfile, compose.yaml и два примера конфигурации.
Соберите `cmd/cerber-sensor` для архитектуры сенсора и положите бинарный файл
`cerber-sensor` рядом с Dockerfile. Создайте каталоги `runtime`, `rules`, `eve`,
`state`, доступные UID/GID 1000; скопируйте `capture.example.json` в
`runtime/runtime.json`, `sensor.example.json` в `sensor.json` и добавьте ранее
полученные реквизиты зарегистрированного агента в `credentials.json` (0600).
В обоих JSON задайте одинаковые интерфейс, режим `span` либо `tap` и путь EVE.
В `sensor.json` задайте адрес SIEM и публичный ключ из каталога правил админки.
Затем запустите `docker compose -f deploy/suricata/compose.yaml up -d --build`.
Никогда не добавляйте реквизиты, рабочие конфигурации и правила в Git.

Движок запускается через `cerber-sensor -capture-config /capture/runtime.json`.
Компонент формирует YAML из шаблона установленного Suricata, проверяет его
через `suricata -T --init-errors-fatal`, затем включает AF_PACKET. Интерфейс и
пути выбираются локально: веб-сервер не может прислать команду захвата или shell.
У существующего сенсора не меняйте транспорт EVE без остановки, копии очереди
и проверки курсора/отпечатка конфигурации. TCP и файловый EVE используют один
источник; одновременное включение обоих на одном агенте запрещено.

## Доставка и ограничения места

Записываются EVE alert и flow с Community ID; payload, packet, HTTP body и
дополнительные журналы выключены. После подтверждённой записи в локальную очередь
курсора достаточно для безопасного продолжения после перезапуска. Очередь
доставляется повторно при сетевых ошибках; SIEM устраняет дубли.

При достижении 16 МиБ сенсор переименовывает EVE и вызывает `reopen-log-files`.
Непрочитанная предыдущая генерация сохраняется; новая ротация ждёт её переноса в
очередь. Журнал намерения позволяет завершить прерванную операцию после рестарта.
Хранятся максимум два файла. Отдельно процесс захвата ограничен RLIMIT_FSIZE:
64 МиБ на файл, то есть до 128 МиБ EVE. При длительном отставании сборщика или
недоступности SIEM лимит может остановить запись/движок: это потеря новых
наблюдений, а не гарантия бесконечной доставки. Восстановите доставку/место и
перезапустите движок при необходимости; не удаляйте непрочитанные файлы и курсор.
Не используйте сторонний logrotate/copytruncate для управляемого EVE.

В карточке сенсора показываются интерфейс, режим, версия и доступность движка,
счётчики принятых/потерянных пакетов, ошибки checksum, объём и состояние EVE,
время проверки. Это данные последнего heartbeat, а накопленный счётчик пакетов
не означает наличие текущего трафика. Отсутствие алертов не доказывает полноту
зеркалирования; настройку SPAN и packet drops проверяйте отдельно.

## Корреляции и расследование

Правило `suricata.alert` создаёт срабатывание по валидному EVE alert. По умолчанию
повторы одинакового SID/сенсора/входа/интерфейса/пары IP/протокола/порта назначения
подавляются на 60 секунд. Все исходные события сохраняются. Администратор может
менять подавление (0–3600 секунд), группы, исключения и включение правила, запускать
проверку без боевых оповещений и откатывать версии параметров. Критичность Suricata
1 → высокая, 2 → средняя, 3/4 → низкая; это не CVSS и не оценка успешности атаки.

Создайте инцидент из срабатывания и откройте его граф. Видны источник, назначение,
наблюдающий сенсор, SID/rev, категория, важность, Flow ID, Community ID и исходный
EVE. Контекст flow добавляется только при совпадении сенсора, входа, интерфейса,
flow_id и двунаправленного кортежа, если время алерта входит в интервал потока
(допуск 1 секунда). Поиск ограничен 30 минутами, 100 кандидатами/512 КиБ и
20 шагами; ограничения отмечаются в графе. Группы и исключения проверяются снова
при открытии контекста. IP не становится автоматически активом, пользователем
или сеансом. Сигналы IDS не запускают автоматическое active response.

## Проверка без физического SPAN

Для отдельного контейнера с `--network none` задайте `mode: test` и
`interface: cerber-span`. Компонент создаёт пару veth `cerber-span`/`cerber-tap`
только в namespace без других интерфейсов, кроме loopback. Эта проверка не меняет
сеть хоста. Правило для безопасного теста:

```text
alert icmp any any -> any any (msg:"CERBER local ICMP echo request"; itype:8; sid:1000001; rev:1;)
```

Назначьте его через админку (или пакет ET Open с этим правилом), затем запустите
`send-test-packet.py` внутри тестового контейнера. Он отправит один ICMP echo в
изолированную пару. Ожидаются EVE alert, затем flow после таймаута потока,
срабатывание `suricata.alert`, исходник и сетевые связи в созданном инциденте.
Тестовый режим явно отмечен в админке и не означает подключённый SPAN предприятия.

Основные механизмы соответствуют документации Suricata:
[EVE](https://docs.suricata.io/en/suricata-7.0.11/output/eve/eve-json-output.html),
[управляющий сокет](https://docs.suricata.io/en/suricata-7.0.11/unix-socket.html).
