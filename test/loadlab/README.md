# Изолированный нагрузочный стенд Suricata → Cerber

Стенд запускает настоящие Suricata, cerber-sensor и сервер SIEM. Требуется Docker
с Linux, минимум 5 ГиБ памяти в VM, Go и Python 3. Используется нативная архитектура
Docker (amd64 или arm64), без эмуляции. Лимит стенда: 4 CPU / 4 ГиБ, 128 процессов.

```sh
python3 test/loadlab/launch.py \
  --rules /absolute/path/to/et-open.rules \
  --output "$PWD/.local/loadlab-new-run"
```

Выходной каталог должен быть новым. Первый build получает Suricata из пакетов
Ubuntu 24.04; фактическая версия, хеш набора правил, архитектура и хеши бинарников
записываются в результаты. Для точного повторения сохраните исходный образ/пакеты
и snapshot правил. Каталог .local не публикуется. Боевые адреса и реквизиты не нужны.

## Изоляция

Контейнер работает с `--network none`, без опубликованных портов и host network.
Единственные дополнительные capabilities — NET_ADMIN/NET_RAW для собственной пары
veth внутри namespace. Корневая ФС read-only; БД и журналы лежат в новом Docker volume.
На старте проверяется отсутствие подключённых сетевых интерфейсов и прежних данных.
Настройки SMTP, ThreatFox, AD и ключи active response не передаются; соответствующие
workers не запускаются. Срабатывания существуют только в тестовой БД.

## Сценарии

* 50, 200 и 800 пакетов/с по 8 секунд, затем ожидание всех контрольных корреляций.
* Отказ локального прокси доставки (HTTP 503), рост durable spool, SIGKILL сенсора
  с непустой очередью, перезапуск и восстановление доставки.
* SIGKILL SIEM при продолжающемся трафике, запуск с прежними БД и догоняющая доставка.
* Потеря успешного HTTP-ответа после сохранения пакета сервером: повторная отправка
  не должна создавать повторных событий или корреляций.
* Корректная остановка/запуск Suricata между сериями и проверка новой серии.
  Захват во время остановленного движка этим сценарием не обещается.

Для длительной проверки добавьте к команде `--sustained` и укажите новый каталог
результатов. Этот профиль подаёт 100 пакетов/с в течение 10 минут (60 000 пакетов),
затем ждёт обработки всех alert и flow. Оба профиля сверяют число событий и
корреляций, проверяют целостность трёх БД и сохраняют замер отставания EVE из
последнего принятого сервером heartbeat. Время heartbeat указано отдельно от
финального замера очередей.

Полный переданный набор правил дополняется одной сигнатурой SID 9900001.
Генератор посылает UDP-маркеры на созданную пару veth; исходные IP уникальны, чтобы
штатное подавление повторов корреляции не выглядело потерей. Пакеты сохраняются в
`traffic.pcap`. Это воспроизводимый контрольный профиль, а не модель произвольной
корпоративной сети или оценка пропускной способности физического SPAN.

Используется один capture worker (`single`, AF_PACKET; Suricata 7 выбирает TPACKET_V2
для этого режима). BPF ограничивает захват контрольным UDP-портом 49000. UDP flow
timeout сокращён до 5 секунд; финальная остановка Suricata сбрасывает flow-записи.
Итого ожидаются один alert и один flow на пакет, одна корреляция на alert.

## Что измеряется

`evidence/result.json` содержит число пакетов, EVE alert, нормализованных alert и
корреляций, расхождения, счётчики capture/drop/checksum, задержки p50/p95/p99,
максимальные очереди и CPU/RSS процессов. `samples.jsonl` — временной ряд примерно
каждые 500 мс. 100% CPU означает одно логическое ядро; память — RSS процесса, не
весь page cache контейнера. CPU процесса измеряется по /proc, включая дочерние
потоки; генератор и наблюдатель не включены в CPU SIEM/сенсора/Suricata.

Задержка приёма: время отправки пакета → сохранённое received_at. Задержка корреляции:
время отправки → первое наблюдение записи в БД; это верхняя оценка с погрешностью
интервала наблюдения. Поле Detection.CreatedAt не используется как время обработки.
Времена берутся на одном узле. Сам наблюдатель создаёт дополнительную нагрузку.

Накопление событий в EVE до чтения, durable spool, очередь нормализации и корреляции
считаются отдельно. Пики — выборочные: короткий всплеск между замерами может быть
выше. Ресурсы и пики включают генерацию и догоняющую обработку внутри каждого этапа;
flow-записи могут дорабатываться на следующем этапе. Проверка полного равенства
всех исходных, нормализованных и EVE-записей выполняется в конце.

Потеря или таймаут завершают стенд с ошибкой, сохраняя диагностику. Успех не означает
нулевую задержку: при перегрузке EVE-файл может накапливать большой непрочитанный хвост.
Стенд не меняет производственные лимиты, правила или параметры сборщика.

После выполнения launcher экспортирует доказательства и удаляет только созданные
им контейнер, volume и образ. Локальные результаты сохраняются, включая диагностические
данные неуспешного прогона. Для повторного запуска укажите другой каталог.

Для экспорта графиков PNG/PDF установите matplotlib в отдельное локальное окружение
и выполните `python test/loadlab/plot.py /absolute/path/to/output/evidence`.
Графики строятся только по сохранённым измерениям; новых тестовых событий не создают.
