# Cerber

Cerber — проект платформы мониторинга безопасности и управления уязвимостями сети.
Первый этап — сканер операционных систем с локальным и сетевым режимами работы.

Автор: **Кислов Роман Сергеевич**. Лицензия: [Apache 2.0](LICENSE).

## Текущее состояние

Реализован первый CLI-прототип на **Go**:

- Добавление и просмотр активов с IPv4/IPv6; создание целей из зарегистрированных активов.
- Создание задач со снимком адресов и параметров сканирования.
- TCP connect-проверки с ограничением параллелизма, таймаутом и отменой через Ctrl+C.
- SQLite-хранилище, история задач и результатов между запусками.
- Транзакционный outbox событий с версионированным envelope и чтением по курсору.
- История инвентаря ОС/ПО и сравнение снимков; локальные Windows- и Linux-коллекторы.
- Централизованный приём отчётов агентов, привязанные к активам токены и устойчивая очередь доставки.
- Сведения WUA об установленных/применимых обновлениях и проверка релизов Microsoft Edge.

Открытый порт — наблюдение о доступности сервиса, а не подтверждённая уязвимость.
Импорт записей БДУ/NVD в модель уязвимостей, matching, удалённые SSH/SMB/WMI-сборщики, GUI, расписания, роли,
API управления сканером и SIEM-корреляция ещё не реализованы. Репозиторий пакетов БДУ описан ниже.

## Быстрый запуск

Требуется Go 1.25+ с автоматическим выбором toolchain: в `go.mod` закреплён Go 1.26.10.
При отключённой автозагрузке установите Go 1.26.10 или новее вручную. CGO не требуется.

```sh
go build -o bin/cerber ./cmd/cerber
./bin/cerber asset add -ip 127.0.0.1 -name localhost
./bin/cerber asset list
```

Подставьте ID из вывода предыдущих команд:

```sh
./bin/cerber target add -name local -assets ASSET_ID
./bin/cerber task create -target TARGET_ID -ports 22,80,443 -concurrency 16 -timeout-ms 1000
./bin/cerber task run -id TASK_ID
./bin/cerber task show -id TASK_ID
./bin/cerber events list -after 0 -limit 100
```

Вывод — JSON. `task run` выполняется синхронно; Ctrl+C сохраняет завершённые проверки
и переводит задачу в `interrupted`. Ошибка соединения записывается отдельно от отказа
в соединении и таймаута. Ошибка записи останавливает выполнение задачи.
Повторный запуск той же задачи запрещён; для нового сканирования создайте новую задачу.

База по умолчанию: `.local/cerber.db`. Общий параметр `-db PATH` указывается **перед** командой:

```sh
./bin/cerber -db .local/demo.db asset list
```

Начальные ограничения одной задачи: 256 активов, 1024 порта, 65536 соединений,
64 одновременных соединения, таймаут 10–30000 мс. Поддерживаются явные IP-адреса
и списки портов; CIDR, DNS discovery и диапазоны портов будут добавлены отдельно.
Применяйте проверки к сетям, на сканирование которых у вас есть разрешение.

## Структура кода

- `internal/domain` — активы, цели, задачи, наблюдения и ограничения.
- `internal/ports` — интерфейсы хранилища, сканера и чтения событий.
- `internal/app` — сценарии приложения и жизненный цикл задачи.
- `internal/scanner/tcp` — ограниченный пул TCP-проверок.
- `internal/storage/sqlite` — SQL-адаптер, версия схемы и транзакционный outbox.
- `internal/event` — контракт событий продукта; независим от брокера и GUI.
- `internal/knowledge` — публикация подписанных XML-пакетов, HTTP-репозиторий и клиентский кэш.
- `internal/inventory`, `internal/collector/windows` — снимки ОС/ПО, покрытие сбора и Windows-адаптер.
- `internal/updates/microsoft` — проверка официального источника релизов Edge.
- `cmd/cerber` — CLI, конфигурация и обработка сигналов.

Доменные данные и события фиксируются одной транзакцией. Это основа будущей
публикации событий с повторной доставкой; сетевой publisher пока отсутствует.
Каждый потребитель сможет хранить собственный курсор. Outbox не является готовым
хранилищем высокочастотных журналов SIEM и пока не очищается автоматически.

Целевая серверная архитектура разделяет сбор, обработку, хранение и корреляцию.
PostgreSQL предназначен для управляющих данных, ClickHouse — для оперативных событий,
объектное хранилище — для архива. Эти адаптеры пока не подключены.
`KnowledgeProvider` обеспечивает проверенный локальный снимок базы перед стартом задачи.
ID, версия и SHA-256 фиксируются вместе с переходом в `running` и событием старта.
TCP-проверки могут работать без базы знаний. SQLite поддерживает миграцию схемы
с сохранением прежних данных.

Desktop-клиент будет использовать то же ядро через адаптер; выбор оболочки после перехода
на Go остаётся открытым. В перспективе: сбор событий, поиск, корреляция и обработка инцидентов.

## Проверка и платформы

```sh
go test -race ./...
go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o bin/cerber-linux-arm64 ./cmd/cerber
```

Целевые платформы: Windows x86_64, Linux x86_64/aarch64. Кросс-сборка не заменяет
проверку запуска на целевой ОС. Установщики пока не выпускаются.

При SIGKILL, отключении питания или падении процесса задача может остаться в `running`.
Автоматическое восстановление и leases ещё не реализованы; не меняйте статус такой задачи,
пока не установлено, что исполнитель остановлен. Полноценного фонового планировщика нет:
параллельно запущенные CLI-процессы имеют отдельные лимиты соединений.

Уведомления о лицензиях зависимостей: [THIRD_PARTY_NOTICES.txt](THIRD_PARTY_NOTICES.txt).

## Централизованный репозиторий БДУ

Сервер публикует исходный XML как неизменяемый пакет. На этом этапе проверяется
структурная корректность XML (UTF-8, без DTD), размер и SHA-256; разбор полей БДУ
и проверка схемы конкретной выгрузки ещё не реализованы. Подпись Ed25519 принадлежит
издателю Cerber и не является подписью ФСТЭК. Сохраняется provenance: адрес загрузки
или признак офлайн-импорта.

Подготовка на сервере:

```sh
./bin/cerber knowledge keygen -dir .local/knowledge-keys
./bin/cerber knowledge publish -file /path/to/vulxml.xml -version 2026-10-19.1 -private-key .local/knowledge-keys/signing.key
```

Вместо файла можно указать `-url HTTPS_URL`: выгрузка будет загружена централизованно
и опубликована после проверки. HTTP-редиректы при загрузке запрещены.
Каждая публикация требует новой версии; сервер присваивает возрастающий номер последовательности.
Обновление пока запускается вручную, автоматического ежедневного расписания нет.

Передайте `signing.pub` исполнителю по доверенному каналу. Закрытый `signing.key`
остаётся у издателя; HTTP-серверу он не нужен. Установите одинаковый случайный токен
длиной от 24 символов в `CERBER_KNOWLEDGE_TOKEN` на сервере и исполнителе.
Токен не передаётся аргументом командной строки.

```sh
# Сервер: команда работает до Ctrl+C.
./bin/cerber knowledge serve -listen 127.0.0.1:8787

# Исполнитель, в другом терминале с тем же токеном:
./bin/cerber knowledge sync -server http://127.0.0.1:8787 -public-key /path/to/signing.pub
./bin/cerber task run -id TASK_ID -knowledge-server http://127.0.0.1:8787 -knowledge-key /path/to/signing.pub
```

Второй запуск проверяет свежий манифест и хеш кэша, повторно XML не скачивает.
Новая версия с тем же содержимым также использует уже проверенный файл.
Кэш содержит XML по SHA-256, подписанные манифесты версий и активный манифест.
Подмена подписи, содержимого, повторное использование версии и откат последовательности
отклоняются. Защита от отката опирается на сохранённое локальное состояние после первой
успешной синхронизации; кэш и доверенный ключ должны быть защищены от локальной подмены.
Ротация ключей и автоматическая очистка старых версий пока не реализованы.

Офлайн-режим включается явно:

```sh
./bin/cerber knowledge sync -offline -public-key /path/to/signing.pub
./bin/cerber task run -id TASK_ID -knowledge-offline -knowledge-key /path/to/signing.pub
```

По умолчанию максимальный возраст **манифеста публикации** — 72 часа, настраивается
`-max-age` у `knowledge sync` и `-knowledge-max-age` у `task run`. Это не возраст записей
БДУ и не гарантия актуальности исходной выгрузки. Офлайн-режим сохраняет проверку возраста.
При ошибке получения или проверки снимка задача остаётся в очереди; тихого перехода
с онлайн-режима на старый кэш нет. Кэш меняется только после проверки полного пакета.

Для доступа по сети используйте HTTPS с доверенным сертификатом:

```sh
./bin/cerber knowledge serve -listen 0.0.0.0:8787 -tls-cert /path/to/server.crt -tls-key /path/to/server.key
```

Plain HTTP разрешён только на явных loopback IP; в том числе клиент не принимает
`http://localhost` или сетевой HTTP-адрес. Альтернатива — TLS reverse proxy перед loopback-сервером.
Read-only API: `GET /v1/knowledge/latest` и `GET /v1/knowledge/packages/{sha256}`;
оба требуют `Authorization: Bearer ...`. Публикация выполняется локальной CLI-командой,
HTTP-загрузки пакетов на сервер нет. Максимум пакета — 512 MiB, манифеста — 64 KiB.

Одновременная запись в один репозиторий или кэш блокируется каталогом `.write-lock`.
После аварийного завершения он может сохраниться: удаляйте его только после проверки,
что предыдущий процесс остановлен. Объекты сначала записываются во временные файлы,
проверяются и синхронизируются, затем переименовываются. Это не заменяет резервное
копирование, и гарантии при потере питания зависят от ОС и файловой системы.

## Инвентаризация и контроль обновлений Windows

Первый Windows-адаптер собирает:

- Название, версию, сборку с UBR, редакцию и архитектуру ОС.
- Зарегистрированные приложения из HKLM/HKCU, в 32/64-битных представлениях реестра:
  имя, исходную строку версии, издателя и ключ происхождения. HKCU-идентификатор включает SID текущего пользователя.
- Опциональные компоненты Windows и их состояния, если запрос разрешён текущему пользователю.
- Установленные обновления, которые возвращает локальная база Windows Update Agent (WUA): UpdateID, revision и KB.
- По явному флагу — применимые, не скрытые software-обновления из настроенного источника WUA (включая WSUS).

Сбор ничего не устанавливает, не меняет политики и не повышает привилегии.
`-check-windows-updates` разрешает сетевой запрос метаданных WUA; без него поиск установленных
обновлений использует локальные метаданные. Автоматического скачивания/установки пакетов нет.
Запрос опциональных компонентов может требовать административных прав: ошибка сохраняется
в покрытии сбора, а не превращается в пустой «успешный» список.

Пример для PowerShell на Windows:

```powershell
go build -o bin/cerber.exe ./cmd/cerber
.\bin\cerber.exe asset add -ip 127.0.0.1 -name local-windows
.\bin\cerber.exe inventory collect-local -asset ASSET_ID
.\bin\cerber.exe inventory collect-local -asset ASSET_ID -check-windows-updates
.\bin\cerber.exe inventory list -asset ASSET_ID
.\bin\cerber.exe inventory show -id SNAPSHOT_ID
.\bin\cerber.exe inventory diff -before OLDER_SNAPSHOT_ID -after NEWER_SNAPSHOT_ID
```

Локальный сбор допускает только актив с loopback-адресом или адресом локального интерфейса.
Для данных удалённой машины предусмотрен импорт JSON того же формата:
`inventory import -asset ASSET_ID -file snapshot.json`. Сам импорт не аутентифицирует
удалённый хост; для сетевой доставки используйте агент с отдельным токеном (см. ниже).
На Linux доступен нативный сбор APT/RPM; на macOS — импорт снимков.

Каждый снимок неизменяем и хранит время сбора, источник и покрытие разделов.
`inventory list` возвращает метаданные и счётчики, полный инвентарь — `inventory show`.
Поздно импортированный старый снимок не вытесняет более новый по времени наблюдения.
Сравнение показывает изменившиеся версии/состояния и новые наблюдения. Отсутствие записи
считается удалением из списка только при полном покрытии соответствующего раздела обоими снимками.

Покрытие нативного Windows-сбора намеренно частичное: реестр не охватывает все portable/Store-приложения
и профили других пользователей; WUA не является полным реестром всех CBS/MSI/сторонних исправлений.
Наличие доступного обновления не означает подтверждённую уязвимость; отсутствие результатов WUA
не доказывает отсутствие пропущенных исправлений. Win32_Product не запрашивается.

### Релизы Microsoft Edge

Источник — официальный [Microsoft Edge enterprise feed](https://edgeupdates.microsoft.com/api/products?view=enterprise).
Привязка к приложению явная: выберите компонент Edge из инвентаря и его реальную архитектуру.
Выбор по одному похожему отображаемому имени не выполняется.

```powershell
.\bin\cerber.exe updates edge -inventory SNAPSHOT_ID -component EDGE_COMPONENT_ID -architecture x64 -channel Stable
.\bin\cerber.exe updates list -asset ASSET_ID
```

Поддерживаются каналы Stable/Beta/Dev и архитектуры x64/x86/arm64.
Каналы, архитектуры и платформы не смешиваются. Сравниваются числовые Windows-версии,
а не строки: 10.0.10.0 новее 10.0.9.0. Нераспознанная установленная версия даёт `unknown`.
Исходная дата публикации сохраняется; даты Microsoft без часового пояса интерпретируются адаптером как UTC.
Ответы и ошибки источника сохраняются в истории с привязкой к снимку инвентаря и событием `updates.checked`.

Результат сообщает о доступном релизе в выбранном канале, но не доказывает совместимость
пакета с конкретной редакцией ОС или политикой поэтапного развёртывания. Проверку можно выполнять
централизованно по импортированным снимкам; это не команда обновления приложения на хосте.

Пока проверки запускаются вручную. Фоновый планировщик, уведомления, полный servicing-инвентарь,
каналы Office Click-to-Run, Store/winget и другие каталоги разработчиков — следующие адаптеры.
Linux использует собственные пакетные менеджеры для выбора кандидатов, включая версии дистрибутива/backport.

## Инвентаризация Linux и обновления APT/RPM

Linux-коллектор читает `/etc/os-release`, архитектуру и версию ядра, установленные
пакеты и, по запросу, кандидаты обновлений из настроенных репозиториев:

- Debian/Ubuntu и Astra Linux: `dpkg-query` и симуляция `apt-get dist-upgrade`.
- РЕД ОС и совместимые RPM-системы: `rpm` и `dnf check-update` (либо `yum`).
- Альт: RPM-база и симуляция APT-RPM; dpkg не используется.

```sh
./bin/cerber inventory collect-local -asset ASSET_ID -check-package-updates
./bin/cerber inventory collect-local -asset ASSET_ID -check-package-updates -refresh-package-metadata
./bin/cerber inventory show -id SNAPSHOT_ID
./bin/cerber inventory diff -before BEFORE_ID -after AFTER_ID
```

Параметр `-package-manager auto|apt|apt-rpm|dnf|yum` позволяет явно выбрать адаптер.
Без `-check-package-updates` собирается только инвентарь. По умолчанию используются
кешированные метаданные, их свежесть неизвестна. `-refresh-package-metadata` запрашивает
репозитории и может потребовать прав на запись кеша; Cerber не запускает sudo.
Ошибка обновления метаданных отмечается в покрытии снимка, а не трактуется как отсутствие обновлений.

Кандидаты находятся в `updates` со статусом `available`, установленной и доступной
версией, архитектурой, источником и режимом метаданных. Снимок фиксирует момент проверки;
`inventory show` не запрашивает репозитории повторно. Поле `coverage` необходимо проверять
вместе с результатами: команды могут завершиться с частичным снимком и ошибкой отдельного раздела.
Уведомления `inventory.recorded` поступают в существующий транзакционный outbox.

Выбор кандидата делегирован пакетному менеджеру: Cerber не сравнивает Debian/RPM-версии
как SemVer. Epoch/release сохраняются, несколько установленных версий RPM (например, ядер)
хранятся набором `installed_versions`. Доступность обновления сама по себе не означает уязвимость.
Новые зависимости, удаления, замены obsoletes и полная применимость плана установки пока
не моделируются; покрытие кандидатов — `partial`, пустой список не означает «ОС актуальна».
Программы вне нативной пакетной базы и журнал пакетных транзакций не собираются.

Команды не устанавливают пакеты и не добавляют репозитории или ключи; используются настройки
пакетного менеджера системы. Автоматическое исправление ОС не реализовано.
Парсеры Astra/РЕД ОС/Альт проверяются фикстурами, нативный APT — в Linux CI x86_64/aarch64.
Проверки на реальных установках российских дистрибутивов ещё требуются.

## Централизованный приём с агентов Windows/Linux

В одном бинарнике доступны независимые режимы `siem serve` и `agent`.
Сервер принимает `POST /v1/agent/reports`: снимок инвентаря, нативные кандидаты
Windows Update/APT/RPM и отдельные проверки приложений, связанные с этим снимком.
Агент сам инициирует соединение; входящий порт на рабочих станциях не требуется.

На сервере создайте актив, затем выпустите отдельные учётные данные агента:

```sh
./bin/cerber -db .local/siem.db asset add -ip 192.0.2.15 -name workstation-15
./bin/cerber -db .local/siem.db siem enroll -asset SERVER_ASSET_ID -out .local/workstation-15.json
./bin/cerber -db .local/siem.db siem serve -listen 0.0.0.0:8790 -tls-cert server.crt -tls-key server.key
```

`siem enroll` создаёт новый файл с секретом (0600 на Unix), не перезаписывает существующий
и не выводит токен в stdout. Передайте файл на соответствующий агент защищённым способом
и ограничьте доступ к нему; на Windows настройте ACL. В серверной БД сохраняется SHA-256 токена.
Каждый токен привязан к серверному активу; присланный агентом локальный `asset_id` заменяется
этой привязкой. IP актива задаёт оператор: сервер не подменяет его адресом NAT/proxy.

На Linux-агенте создайте локальный актив и запустите периодический сбор:

```sh
./bin/cerber -db .local/agent.db asset add -ip 127.0.0.1 -name this-machine
./bin/cerber -db .local/agent.db agent run -asset LOCAL_ASSET_ID -credentials agent.json -server https://siem.example:8790 -ca-cert organization-ca.pem -interval 1h -check-package-updates
```

На Windows используется тот же протокол и отдельная локальная БД:

```powershell
.\bin\cerber.exe -db .local/agent.db asset add -ip 127.0.0.1 -name this-machine
.\bin\cerber.exe -db .local/agent.db agent run -asset LOCAL_ASSET_ID -credentials agent.json -server https://siem.example:8790 -ca-cert organization-ca.pem -interval 1h -check-windows-updates
```

`-ca-cert` необязателен, если сертификат сервера уже доверен системой. Проверка сертификата
и имени узла не отключается; перенаправления HTTP не выполняются. Открытый HTTP разрешён
только для явного loopback IP, например `http://127.0.0.1:8790`, при локальной отладке.
`agent run` работает в foreground до Ctrl+C; для фонового режима предусмотрены
[systemd](deploy/linux/README.md) и [Windows Service](deploy/windows/README.md). Интервал сбора — от минуты до суток.
При сбоях отправка повторяется с паузой до пяти минут; доступные данные сохраняют исходное
время сбора, а квитанция отдельно фиксирует серверное время приёма.

Разовый сбор и управление доставкой:

```sh
# Собрать и поставить в устойчивую локальную очередь, без сети:
./bin/cerber -db .local/agent.db agent collect -asset LOCAL_ASSET_ID -credentials agent.json -check-package-updates
# Отправить очередь; неподтверждённые отчёты останутся в ней:
./bin/cerber -db .local/agent.db agent flush -credentials agent.json -server https://siem.example:8790 -ca-cert organization-ca.pem
# Передать ранее собранный снимок вместе со всеми сохранёнными для него проверками:
./bin/cerber -db .local/agent.db agent enqueue -inventory SNAPSHOT_ID -credentials agent.json
```

Для Linux доступен явный `-refresh-package-metadata` вместе с `-check-package-updates`;
по умолчанию используются кешированные метаданные. Windows онлайн-проверка включается
через `-check-windows-updates`. Покрытие и ошибки отдельных разделов передаются без
повышения статуса: частичный сбор на сервере остаётся частичным.

Отдельные результаты `updates edge`, выполненные после сбора, отправляются новым
`agent enqueue -inventory SNAPSHOT_ID`. Очередной отчёт включает снимок и проверки в
состоянии на момент постановки в очередь, последующие изменения в него не дописываются.
Самостоятельное планирование проверок Edge в `agent run` пока не реализовано.

Просмотр данных выполняется на сервере существующими командами:

```sh
./bin/cerber -db .local/siem.db inventory list -asset SERVER_ASSET_ID
./bin/cerber -db .local/siem.db inventory show -id SERVER_SNAPSHOT_ID
./bin/cerber -db .local/siem.db updates list -asset SERVER_ASSET_ID
./bin/cerber -db .local/siem.db events list -after 0
./bin/cerber -db .local/siem.db siem revoke -agent AGENT_ID
```

Нативные кандидаты обновлений находятся в `inventory show` → `updates`; `updates list`
показывает отдельные проверки приложений. Серверные ID отделены от локальных и включают
пространство имён агента. Повторное получение одного отчёта возвращает прежнюю квитанцию;
изменённое содержимое под тем же ID отклоняется с HTTP 409. Повторно присланный неизменный
снимок с новыми проверками не дублирует инвентарь. Снимок, проверки, квитанция и события
`inventory.recorded`, `updates.checked`, `agent.report_received` записываются одной транзакцией.
События содержат `source=agent:AGENT_ID` для последующей обработки и корреляции.
Отзыв токена блокирует новые запросы и повторы уже принятых отчётов.

Ограничения текущего контура: один снимок до 32 MiB, отчёт до 40 MiB и 100 отдельных
проверок; локальная очередь до 100 отчётов / 256 MiB, без молчаливого удаления старых данных.
Переполнение и постоянные ошибки авторизации/конфликта требуют вмешательства оператора;
первый неподтверждённый отчёт блокирует последующие отчёты этого агента. Снимки сохраняются
локально до постановки в очередь: при аварии между этими шагами их можно отправить вручную
через `agent enqueue`. Подтверждённые отчёты удаляются из очереди, локальная история инвентаря
остаётся; автоматическая очистка локальной истории и серверное хранение инвентаря
по сроку пока не реализованы. Сроки хранения событий настраиваются отдельно.
Приём — SQLite/WAL с сериализацией записей и транзакционным outbox. Это первый серверный
контур SIEM; брокер, распределённое хранилище и mTLS ещё не реализованы.

CI включает нативную доставку Linux-инвентаря с кешированными APT-кандидатами на x86_64/aarch64
и локального Windows-инвентаря без онлайн-поиска WUA. Онлайн WUA/WSUS и российские
дистрибутивы требуют отдельных стендовых проверок; передача результатов проверяется также фикстурами.

## Фоновый агент и конфигурация

`agent run -config ABSOLUTE_FILE` читает строгий JSON-конфиг; одновременно передавать
другие параметры или переопределять `-db` нельзя. Все пути — абсолютные, токен хранится
отдельно. `agent validate-config -config ABSOLUTE_FILE` проверяет входные файлы без сети
и создания/миграции БД. Примеры и установка: [Linux/systemd](deploy/linux/README.md),
[Windows/SCM](deploy/windows/README.md). Windows-режим `agent service-run -config FILE`
предназначен для SCM; в консоли используйте обычный `agent run`.

Сборка Windows использует `golang.org/x/sys/windows/svc`; дополнительная программа-обёртка
не требуется. Windows-агент пишет служебные сообщения в Application/CerberAgent, Linux —
в journal. Проверяйте покрытие инвентаря: ограниченная служебная учётная запись может видеть
меньше данных, чем интерактивный администратор. Ротация токенов, retention и MSI/DEB/RPM
установщики в этот этап не входят.

## Состояние агентов и свежесть инвентаря

```sh
./bin/cerber -db .local/siem.db siem agents
./bin/cerber -db .local/siem.db siem agents -asset SERVER_ASSET_ID -offline-after 15m -inventory-max-age 26h
./bin/cerber -db .local/siem.db siem agents -limit 100 -after AGENT_ID
```

Результат содержит `as_of`, применённые пороги, массив `agents` и `next_cursor`, если
есть следующая страница. По умолчанию выводится до 100 агентов; максимум страницы — 1000.
Токены и их хеши в реестр не попадают. Команда выполняется на сервере с доступом к его БД;
для сетевого доступа используйте защищённую панель `/admin` (см. ниже).

Каждый агент показывает независимые оценки:

- `contact_status`: `never_seen`, `online`, `offline`, `revoked`. Последний успешный
  приём heartbeat или отчёта обновляет `last_seen_at` по **серверному** времени.
  `online` означает недавний контакт, а не непрерывную проверку доступности процесса.
- `inventory_status`: `missing`, `fresh`, `stale` — возраст самого нового принятого
  снимка по времени сбора. Запоздалый старый отчёт или heartbeat не делают инвентарь свежим.
  `latest_inventory_id` связывает состояние с полным снимком и его покрытием.
- `health_status`: `missing`, `fresh`, `stale` — возраст последнего принятого heartbeat.
  Устаревшие сведения об очереди не считаются текущими: `queue_status=unknown`, но исходные
  последние наблюдения доступны в `health` с `last_heartbeat_at`.
- `health.collection_status`: `not_attempted`, `complete`, `partial`, `error` — последняя
  попытка сбора в текущем процессе; исходные ограничения/ошибки остаются в покрытии снимка.
  `health.delivery_status`: `not_attempted`, `ok`, `error` — последняя попытка доставки отчёта.
  Успешный heartbeat сам по себе не переводит доставку отчётов в `ok`.
- `health.queue_reports` / `queue_bytes`: неподтверждённые отчёты именно этого агента,
  не полный размер БД/WAL на диске. При недоступности локальной БД `queue_known=false`.
  Актуальная оценка очереди: `unknown`, `empty`, `pending`, `full`.

`agent run` и системные службы автоматически отправляют `POST /v1/agent/heartbeat`.
По умолчанию — раз в минуту, отдельно от цикла сбора/повторной доставки. Настройка:
`-heartbeat-interval 1m` либо JSON-поле `heartbeat_interval` (1m–1h). Старые JSON-конфиги
без этого поля используют 1m. Остановка службы отменяет и дожидается завершения heartbeat;
каждый запрос ограничен десятью секундами. Heartbeat не ставится в устойчивую очередь:
при сетевом сбое передаётся следующее актуальное наблюдение, а не история пропущенных пульсов.

Выбирайте `offline-after` с запасом относительно heartbeat-интервала и сетевых задержек;
`inventory-max-age` — с запасом относительно интервала сбора. По умолчанию пороги 15m и 24h.
Разовые `agent collect` и `agent flush` не запускают фоновый heartbeat. Старые агенты без
heartbeat обновляют контакт только принятыми отчётами; для них учитывайте интервал доставки.
`fresh` обозначает возраст наблюдения, не отсутствие уязвимостей и не свежесть кеша APT/RPM.

Heartbeat использует ту же привязку токена к активу, TLS и отзыв, что и отчёты, но отдельный
лимит тела 4 KiB и отдельные слоты приёма. Часы агента видны в `observed_at`, но не управляют
оценкой связи. Сохраняется только последнее состояние heartbeat, без накопления каждого пульса.
Событие `agent.health_changed` записывается атомарно лишь при изменении категории сбора,
доставки или очереди; изменения счётчиков внутри одной категории и времён не заполняют outbox.
Пороговые online/offline/fresh/stale вычисляются при чтении реестра. Запущенный `siem serve`
дополнительно создаёт устойчивые предупреждения в фоне (см. ниже); исторический time series
мониторинг пока не реализован.

Миграция БД v4 → v5 восстанавливает время последнего контакта и нового инвентаря из уже
принятых отчётов. Повторная доставка подтверждённого отчёта обновляет время контакта без
дублей событий, при этом квитанция сохраняет первоначальное время приёма.

## Автоматические предупреждения

`siem serve` проверяет агентов сразу при запуске и далее раз в 30 секунд, независимо
от поступления heartbeat. Пороги задаются серверу:

```sh
./bin/cerber -db .local/siem.db siem serve -listen 127.0.0.1:8790 \
  -offline-after 15m -inventory-max-age 24h -monitor-interval 30s
```

`agent_offline` (critical) возникает после отсутствия принятых контактов дольше порога;
`inventory_stale` (warning) — когда последний принятый снимок старше порога. Для нового
агента без контактов/инвентаря отсчёт льготного периода начинается с регистрации. Отозванные
агенты не создают новых предупреждений, их открытые предупреждения закрываются при проверке.
Интервал проверки — 5s–1h; пороги связи 1m–24h, инвентаря 1m–365d. Фактическая задержка
обнаружения включает интервал проверки и время прохода по агентам.

Одно условие даёт одно открытое предупреждение на агент. Повторные проверки и перезапуск
сервера его не дублируют. После снятия условия записывается закрытие; новая потеря связи
создаёт новый эпизод. Подтверждение означает ознакомление, сохраняет проблему открытой и
не переносится на следующий эпизод. Изменение порогов может снять условие без новых данных;
причина закрытия `condition_cleared` не утверждает, что хост был исправлен. Доказательства
`evidence` фиксируются на момент обнаружения, а не обновляются при каждом проходе.

```sh
./bin/cerber -db .local/siem.db siem alerts -state active
./bin/cerber -db .local/siem.db siem alerts -state resolved -limit 100
./bin/cerber -db .local/siem.db siem acknowledge -id ALERT_ID
./bin/cerber -db .local/siem.db siem evaluate-alerts -offline-after 15m -inventory-max-age 24h
```

Результат списка включает `items` и `next_before`; `-before SEQUENCE` загружает следующую
страницу в обратном порядке времени создания. Однократный `evaluate-alerts` использует свои
пороги; для постоянной работы задайте их `siem serve`. Веб-панель показывает политику и
состояние фоновой проверки. Запускайте один монитор/сервер на одну БД с единой политикой.
Предупреждения и события `alert.raised`, `alert.resolved`, `alert.acknowledged` записываются
вместе транзакционно; подтверждения различают источник `cli` и `administrator`.

Предупреждения доступны в SIEM и транзакционном outbox. Почтовая рассылка, Telegram,
webhook-доставка, эскалации и правила дежурств пока не подключены. Если сервер остановлен,
проверки не выполняются; при запуске монитор оценивает текущее состояние заново.

## Веб-панель администратора

Панель входит в Go-бинарник: HTML/CSS/JS встроены через embed, CDN и отдельный Node-сервер
не нужны. Создайте первую именную учётную запись через локальную CLI и включите панель:

```sh
# Подготовьте вне Git приватный файл с паролем (12–256 байт UTF-8).
# На Unix ограничьте права до 0600; на Windows — ACL владельца.
./bin/cerber -db .local/siem.db siem user-add -username admin -role administrator \
  -password-file .local/admin-password.txt
./bin/cerber -db .local/siem.db siem serve -listen 127.0.0.1:8790 -admin
```

Откройте `http://127.0.0.1:8790/admin/` и введите имя и пароль. Пароль CLI читает из
файла, не из аргумента командной строки, и не выводит. После создания записи удалите
исходный файл пароля по принятой у вас политике. Без `-admin`/`-admin-key` панель отключена.
В БД сохраняется PBKDF2-HMAC-SHA256 (600 000 итераций, отдельная случайная соль 128 бит).

Для сетевого доступа используйте TLS непосредственно на сервере:

```sh
./bin/cerber -db .local/siem.db siem serve -listen 0.0.0.0:8790 \
  -tls-cert server.crt -tls-key server.key -admin
```

Совместимость со старой установкой: `siem admin-keygen -out FILE` и `-admin-key FILE`
ещё поддерживаются **только пока в БД нет именных пользователей**. На странице входа
оставьте имя пустым, в поле пароля введите прежний ключ; затем создайте администратора
в разделе «Учётные записи». Первая именная запись должна быть активным администратором.
После её создания общий ключ и все его сеансы перестают работать, включая после рестарта.
Перейдите на `-admin`; старый ключ больше не нужен.

Первый интерфейс включает сводку инфраструктуры, страницы агентов и предупреждений,
фильтры, поиск **на текущей странице**, подтверждение предупреждений и просмотр последнего
инвентаря: ОС/версия, покрытие, программы/компоненты и нативные кандидаты обновлений.
Инвентарь отдаётся по 50 записей; не загружается целиком в браузер. Предупреждения и агенты
имеют серверную пагинацию. Автообновление — раз в 30 секунд в активной вкладке. Ошибка
загрузки показывается явно; прежние сведения не подменяются успешным пустым результатом.
Отдельные vendor checks (`updates edge`) пока просматриваются через CLI `updates list`.

Административная сессия — случайная cookie HttpOnly/SameSite=Strict (Secure при TLS),
действующая до 8 часов. Токен не сохраняется в localStorage/sessionStorage и не попадает в URL.
Сессии хранятся в памяти, ограничены по числу и теряются при перезапуске. Выход аннулирует
текущую сессию на сервере. POST-запросы проверяют точный Origin и CSRF-токен; JSON-инвентарь
отрисовывается как текст. Есть ограничения попыток входа и CSP без сторонних скриптов.
Токен агента не даёт доступа к административному API. Для reverse proxy сохраняйте Host и
TLS до Go-сервера: произвольные X-Forwarded-* для Origin/защиты cookie не учитываются.

Права проверяются сервером, в том числе при отправке запросов вручную:

- **Администратор** — просмотр, подтверждение предупреждений, регистрация/отзыв агентов,
  создание пользователей, смена роли, блокировка и установка нового пароля.
- **Оператор** — просмотр, подтверждение предупреждений, регистрация/отзыв агентов.
- **Наблюдатель** — только просмотр инфраструктуры, инвентаря и предупреждений.

Раздел «Учётные записи» доступен администратору. Нельзя заблокировать или понизить последнего
активного администратора. Смена роли, пароля или блокировка аннулирует все сеансы пользователя
на следующем запросе. Изменяющие операции повторно проверяют версию и роль пользователя в той
же транзакции, где записывают результат и событие аудита. Успешные входы и действия управления
попадают в outbox (`events list`) с именем пользователя, без паролей и токенов.
При потере доступа владелец серверной БД может локально создать нового администратора через
`siem user-add`; CLI требует доверенного доступа к файлам сервера.

В разделе агентов нажмите «Зарегистрировать агента»: укажите имя/IP нового актива или ID
существующего. Сервер создаёт привязку и выдаёт файл `agent_id`/`token` для скачивания.
Он совместим с `agent run -credentials FILE`; сервер сохраняет только хеш токена.
Скачайте файл до закрытия формы и передайте по защищённому каналу, ограничив права файла.
Повторного просмотра токена нет. При потере файла отзовите регистрацию и создайте новую.
В карточке агента «Отозвать доступ» немедленно запрещает heartbeat и доставку отчётов;
история и инвентарь сохраняются. Отзыв не останавливает службу на самом узле.
Сканирование, установка обновлений, SSO и MFA через панель пока не реализованы.
Миграция БД v6 → v7 добавляет учётные записи и сохраняет существующие данные.

## Удалённые задания и расписания агентов

Обновите **сервер и агентские бинарники**, затем перезапустите службы агентов. Уже работающий
`agent run` новой версии опрашивает сервер заданий в своём цикле доставки: обычно раз в 30 секунд,
при ошибках доставки — до 5 минут. Старые агенты продолжают отправлять инвентарь/heartbeat,
но не забирают задания. Учётные данные и конфигурация служб остаются прежними.

В карточке активного агента доступны «Собрать инвентарь», «Проверить обновления» и «Расписание».
Действия разрешены администраторам и операторам; наблюдатели видят историю и результаты.
Права повторно проверяются в транзакции постановки/отмены задания или изменения расписания.
Протокол разрешает только `inventory` и `updates`, без команд оболочки, путей, URL или скриптов.

Проверка обновлений собирает новый инвентарь и нативных кандидатов: Windows обращается к
настроенной службе WUA/WSUS, Linux использует настроенный APT/DNF/YUM/APT-RPM. По умолчанию
Linux читает кеш; флажок формы явно запрашивает обновление метаданных. Права службы и доступность
репозиториев не меняются: ошибка прав/источника отражается в покрытии и статусе задания.
Флаги `check_*_updates` конфигурации управляют автономным сбором; удалённое задание `updates`
явно запрашивает проверку независимо от этих флагов. Автоматическая установка пакетов и KB отсутствует.
Кандидаты APT/RPM по-прежнему имеют частичное покрытие применимости, поэтому такое задание может
завершиться частичным результатом даже при успешном запросе менеджера пакетов.

Раздел «Задания» показывает очередь, выполнение/доставку, успешные и частичные результаты,
ошибки, отмену и тайм-ауты. У полученного результата есть ссылка на **снимок этого задания**,
а не только на последний инвентарь узла. Страницы ограничены 100 записями; автообновление — 30 секунд.
«История заданий» в карточке фильтрует историю по агенту; «Все агенты» снимает фильтр.

Расписание задаётся интервалом 1–43 200 минут (до 30 дней) и временем первого запуска.
Форма использует местное время браузера, сервер сохраняет UTC. Можно менять параметры,
приостанавливать и включать расписания; включение ставит первый запуск сразу. Изменение и пауза
затрагивают будущие запуски, уже созданные задания сохраняются. Планировщик работает на сервере
каждые 15 секунд, его состояние видно в панели. После простоя создаётся один актуальный запуск,
пропущенные интервалы не воспроизводятся пачкой. Если предыдущее задание этого расписания ещё
ожидает/выполняется, новый запуск пропускается с событием аудита. На агента допускается до 20
расписаний и 20 незавершённых заданий; при заполнении очереди очередной интервал пропускается.
Расписания сохраняют действие после блокировки автора — управление ими остаётся у других операторов.

Задание ожидает агента до 24 часов; на выполнение и доставку после выдачи отводится 10 минут.
Сбор ограничен локальным тайм-аутом до 5 минут (нативный коллектор — до 3 минут). Один агент
получает одно удалённое задание одновременно; его штатный сбор и удалённый сбор выполняются
последовательно, heartbeat работает независимо. Отменить через UI можно только ожидающее задание.
Отзыв агента запрещает его запросы немедленно; планировщик отменяет незавершённые задания
и отключает расписания. Это не команда остановки процесса на самом узле.

Локальный SQLite-журнал сохраняет факт начала и готовый результат. После перезапуска готовый
результат доставляется повторно без повторения сбора; прерванный сбор получает ошибку `interrupted`.
Успех/частичный результат принимаются сервером только при наличии принятого отчёта этого агента.
Повторное подтверждение идемпотентно. При потере ответа на выдачу задания выполнение остаётся
неизвестным до тайм-аута; истёкшее задание автоматически повторно не выдаётся. Поздний инвентарь
может быть принят отдельно, но не превращает тайм-аут задания в успех.
События постановки, старта, завершения, отмены, пропуска и изменения расписаний записываются
в транзакционный outbox. Миграция БД v7 → v8 добавляет таблицы очереди, расписаний и локального журнала.


## Группы агентов и массовые операции

Раздел «Группы» позволяет создавать и переименовывать группы, менять состав, запускать
инвентаризацию и проверку обновлений сразу для группы. Управление доступно администраторам
и операторам; наблюдателям доступно чтение. Группы являются способом выбора адресатов,
а не границей разграничения доступа между операторами. Один агент может входить в несколько
групп; максимум — 500 агентов в группе, до 100 добавлений за одну операцию.

Массовый запуск атомарно фиксирует адресатов и создаёт отдельное задание каждому агенту.
Карточка запуска показывает общую сводку, состояния участников и ссылки на снимки результатов.
Отозванный агент или заполненная очередь отмечаются как пропуск с причиной, а не успешная проверка.
Изменение состава и названия группы не меняет историю созданного запуска. При конкурентном
изменении группы форма потребует обновить данные перед повторной отправкой.
Отмена массового запуска отменяет только ожидающие задания, сохраняя выполняющиеся и готовые результаты.

Групповое расписание задаётся интервалом от 1 минуты до 30 дней и временем первого запуска.
Допускается до 20 расписаний на группу. При каждом интервале адресаты выбираются заново из
текущего состава. Если агент ещё ожидает или выполняет предыдущее задание этого группового
расписания, он пропускается; остальные участники получают свои задания независимо от него.
Пустая группа получает запуск без адресатов со статусом «Пустой запуск».
Планировщик обрабатывает до пяти групповых расписаний за цикл; после простоя пропущенные
интервалы объединяются в один актуальный запуск. Пауза и редактирование затрагивают будущие
запуски. Архивирование сохраняет состав и историю и отключает групповые расписания;
восстановление группы оставляет их приостановленными до явного включения.

Изменения состава, массовые запуски, отмены и расписания записываются в транзакционный outbox.
Миграция БД v8 → v9 добавляет группы и связи массовых запусков. Для этой функции достаточно
обновить сервер, если агенты уже поддерживают удалённые задания предыдущего этапа:
формат выдачи заданий агентам v1 остаётся прежним.

## События безопасности и первые корреляции

Сбор включается явно. На сервере укажите отдельный файл журнала:

```sh
cerber -db /var/lib/cerber/control.db siem serve -admin \
  -events-db /var/lib/cerber/events.db \
  -listen 127.0.0.1:8790
```

Для сетевого доступа добавьте существующие параметры TLS. Файлы событий и управляющей БД
должны различаться. На агенте добавьте `"event_sources": "journald"` в конфигурацию Linux
или `"event_sources": "windows:Security,windows:System,windows:Application"` в конфигурацию
Windows, затем перезапустите службу. Аналогичный CLI-параметр: `agent run -event-sources ...`.
Обновление сервера выполняется перед обновлением агентов. Функция не меняет схему инвентаризации.

Linux читает systemd journal через `journalctl`, Windows — нативный Event Log через
`Get-WinEvent`. При первом включении берутся последние 100 доступных записей каждого источника;
историческая выгрузка всего журнала не выполняется. Далее чтение идёт вперёд от сохранённого
курсора страницами до 100 записей, цикл — каждые 10 секунд. Windows сохраняет номер записи
и время как защиту от повторного использования номера после очистки канала.
Отсутствующий/устаревший курсор или ошибка доступа останавливают этот источник с диагностикой
в журнале службы; автоматического сброса позиции с потерей истории нет.

Службе Linux необходимо право чтения системного журнала: например, администратор добавляет
`SupplementaryGroups=systemd-journal` в drop-in systemd-службы, если такая группа предоставлена
дистрибутивом. Для Windows настройте чтение выбранных каналов учётной записью службы;
особенно проверьте Security. Установка агента сама этих прав не расширяет. Непривилегированное
чтение journald может показывать только доступную часть журнала. Ограничения и ошибки сборщика
видны в журнале службы; состояние доставки инвентаря не является доказательством сбора событий.

Очередь агента находится в отдельном файле `<agent database>.events`: SQLite WAL,
`FULL` synchronous, курсор источника и пакет фиксируются одной транзакцией. Лимит — 1000 пакетов
или 256 МиБ полезной нагрузки. При заполнении источник не продвигается; записи не вытесняются.
Подтверждение сервера выдаётся после устойчивой записи исходников и квитанции. Повторная доставка
идемпотентна; изменённый пакет с прежним ID отвергается. Актив и агент привязываются сервером
к учётным данным агента. Отзыв запрещает новые запросы; уже допущенный запрос может завершиться.

В этой поставке серверное хранение — отдельный SQLite-адаптер для небольших установок,
а не кластерное хранилище SIEM. Предел учтённой исходной нагрузки и квитанций — 1 ГиБ; после него сервер
перестаёт подтверждать новые пакеты, сохраняя ранее принятые. Нормализованные записи, индексы и WAL требуют дополнительного места. Архивирование и сроки хранения
настраиваются отдельно в разделе «Хранение и архивы»; по умолчанию обслуживание выключено.
Нативная запись ограничена 16 КиБ, пакет — 2 МиБ: превышение сохраняет позицию и требует
разбора оператором. Перед заполнением необходимо обеспечить место и резервную копию;
не удаляйте исходники вручную, пока они используются как доказательства срабатываний.

Нормализатор и коррелятор имеют независимые долговечные позиции и отдельные контракты от
сборщика и HTTP-приёмника. Нормализатор `native-auth/1` распознаёт Windows Security 4624/4625,
1102 и англоязычные сообщения входа OpenSSH с доверенными полями journald `_UID=0` и `_EXE`.
Другие записи сохраняются системными, непонятная структура/время — в карантине вместе с
исходником. Сохраняются JSON-поля journald и данные Event Log с исходным XML; это не захват
двоичных EVTX/journal-файлов и не заявление о соответствии OCSF.

Правила версии 1:

- `auth.repeated_failures`: минимум 5 отказов за 5 минут для одного агента, пользователя и IP.
- `auth.success_after_failures`: успешный вход после такой серии.
- `windows.audit_log_cleared`: событие Security 1102.

Окна используют время источника, обработка — порядок приёма. Поздний отказ участвует в будущих
проверках, но уже обработанный успешный вход задним числом не пересчитывается. События более
чем на 5 минут из будущего попадают в карантин. Повторные серии одного ключа подавляются на
5 минут; доказательства ограничены 100 отказами плюс текущая запись. Это признаки для проверки
оператором, а не доказательство атаки. Пароли, команды реагирования и установка ПО не выполняются.

Раздел «События и корреляции» показывает журнал с фильтрами класса/карантина, счётчики конвейера,
источники и доказательства срабатываний. Оператор/администратор могут подтвердить ознакомление;
подтверждение с автором фиксируется атомарно в аудите событий и не удаляет срабатывание.
Наблюдателю доступно чтение. Правила пока фиксированы в коде; редактора Sigma, межхостовых
корреляций и ClickHouse/S3 в этой поставке нет. Карточки расследований доступны в разделе «Инциденты ИБ».

Нативные интерфейсы: [journalctl](https://www.freedesktop.org/software/systemd/man/248/journalctl.html),
[Get-WinEvent](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.diagnostics/get-winevent?view=powershell-5.1).

## Доменный вход через Active Directory / LDAPS

Сначала создайте именованные записи Cerber и назначьте им роли обычным способом. Одну отдельную
локальную административную запись сохраните для обслуживания. Укажите соответствия локального
имени и UPN пользователя AD, а также DN групп для используемых ролей: пример —
[deploy/directory/ldaps.example.json](deploy/directory/ldaps.example.json).
Пароль сервисной учётной записи хранится в отдельном локальном файле, не в JSON/CLI.
Ограничьте доступ к этому файлу учётной записью серверной службы. Затем запустите сервер с
`-admin -directory-config /etc/cerber/ldaps.json`.

Пользователь входит под **локальным именем из users** и паролем AD. Требуются одновременно
активная локальная запись с назначенной ролью, найденный UPN AD и членство в группе,
указанной именно для этой роли. Вложенное членство проверяется правилом AD
[LDAP_MATCHING_RULE_TRANSITIVE_EVAL](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/4e638665-f466-4597-93c4-12f2ebfabab5).
Автоматического создания учётных записей, назначения administrator и наследования ролей нет.
Для сопоставленного пользователя вход по локальному паролю запрещён. Остальные локальные
пользователи сохраняют обычный вход. Создавайте доменным записям случайные локальные пароли,
не используемые для входа; изменение такого пароля в Cerber не меняет пароль AD.

Поддерживается только `ldaps://`, TLS от 1.2 с обязательной проверкой имени и цепочки сертификата;
можно добавить доменный CA. Проверяются отключение AD-учётной записи, истечение срока и
вычисляемая блокировка/истечение пароля, если AD предоставляет эти атрибуты. Пароль пользователя
проверяется bind и не сохраняется. Все операции имеют сетевые тайм-ауты и ограничение параллелизма.
Локальная блокировка/изменение роли прекращают сессию при следующем запросе. Доступ AD
перепроверяется по запросу не реже одного раза в 30 секунд; отказ каталога или утрата членства
прекращают сессию. Сессия имеет общий предел 8 часов, после перезапуска сервера требуется вход.
Успешный вход попадает в продуктовый аудит с методом `ldaps`.

Реальный контроллер AD требуется проверить в вашем контуре: CA, права чтения сервисной записи,
UPN, DN групп и политика LDAP. Автотесты проверяют запрет plaintext, конфигурацию, обработку
блокировок, разделение локального/доменного пароля и отзыв сессии с тестовым провайдером.
Kerberos/NTLM SSO не включены. OIDC подключается отдельным провайдером, описанным ниже.


## Корпоративный SSO / OpenID Connect

OIDC включается флагом `siem serve -admin -oidc-config /etc/cerber/oidc.json`. Пример:
[deploy/directory/oidc.example.json](deploy/directory/oidc.example.json).
На странице входа появляется «Войти через корпоративный SSO»; пароль вводится у провайдера,
а Cerber получает код авторизации и проверенный ID token. Поддерживается стандартный провайдер
OIDC с discovery/JWKS, например Keycloak; конкретный корпоративный провайдер необходимо
проверить в вашем контуре. Внешние адреса — HTTPS с проверкой CA; HTTP разрешён только для
буквального loopback-IP при локальных испытаниях. Redirect URL должен точно совпадать с
зарегистрированным у провайдера адресом `/admin/oidc/callback` и адресом консоли.

`users` сопоставляет уже созданные локальные имена Cerber со стабильным `sub` данного issuer.
Адрес почты и отображаемое имя не являются ключом доступа. Требуются активная локальная запись,
её роль и точное членство в группе из `role_groups` для этой роли. Провайдер должен включать
в ID token claim `groups_claim` в виде массива строк. Вложенные claim-пути не поддерживаются;
настройте mapper провайдера. Дополнительные scope можно перечислить в необязательном `scopes`.
По умолчанию запрашиваются `openid profile`. Для public client исключите `client_secret_file`;
для confidential client храните secret в отдельном файле с ограниченным доступом.

Поток использует одноразовые state, nonce, cookie привязки браузера и PKCE S256. Проверяются
подпись RS256/ES256/PS256, issuer, audience, срок, время выпуска, nonce и `azp`, если он задан
или audiences несколько. Неверный/повторный callback не создаёт сессию. Незавершённые входы
живут до 5 минут, число и частота попыток ограничены. Access/refresh/ID tokens не сохраняются
в БД или браузерном хранилище. Сессия Cerber ограничена 5 минутами и сроком ID token;
после этого вход повторяется через провайдера, который может использовать свою SSO-сессию.
Локальная блокировка и изменение роли действуют при следующем запросе. Изменения групп или
блокировка у провайдера учитываются при следующем SSO-входе; back-channel logout и token
introspection пока отсутствуют. Успешный вход отмечается в аудите методом `oidc`.

LDAPS и OIDC можно включить вместе для разных локальных имён; одна запись не может быть
одновременно сопоставлена обоим провайдерам. Сопоставленные OIDC-пользователи не могут входить
по локальному паролю. Оставьте отдельную локальную административную запись для обслуживания.
Автотесты поднимают тестовый issuer и JWKS с RSA-подписью и проверяют положительный поток,
PKCE, nonce, state/cookie, подпись, issuer/audience/azp, истечение срока, группы, `sub`, повтор
callback и локальную блокировку. Реальный корпоративный IdP в этих тестах не используется.


## Объяснение корреляций и контроль сборщиков событий

У каждого срабатывания в разделе «События и корреляции» доступно «Почему сработало».
Карточка использует точные ID и версию правила, показывает условия, область действия, окно,
порог, связанные узел/пользователя/IP и период, ограничения, возможные ложные срабатывания,
порядок проверки и первичные источники. Неизвестная версия не заменяется описанием текущей.
Справочник встроенных правил доступен авторизованным пользователям через
`GET /admin/api/correlation-rules`; отдельная версия — `?id=...&version=1`.
Эти записи описывают корреляции SIEM, а не уязвимости из БДУ.

Карточка агента отдельно показывает состояние событий: включён ли сбор, состояние каждого
источника, последнее успешное чтение, пакеты и байты локальной очереди, доставку и последнее
подтверждение. Ошибки чтения/курсора/прав передаются ограниченным кодом, подробная диагностика
остаётся в локальном журнале службы. При заполнении очереди показывается блокировка с
сохранением позиции. Последнее успешное чтение/доставка сохраняются в памяти службы при
последующих ошибках; после её перезапуска состояние заново устанавливается наблюдениями.
Пустой источник может успешно читаться без новых событий. Подтверждённая доставка означает
успешное принятие пакета, а не полноту источника или отсутствие проблем безопасности.

Состояние передаётся независимым heartbeat; обновление обычно видно в пределах его интервала
(по умолчанию минута), цикл событий — 10 секунд плюс время нативного чтения и доставки.
Устаревший heartbeat/наблюдение помечаются явно. У старых агентов без этого поля состояние
неизвестно; хороший инвентарь не подменяет контроль событий. Новые агенты сообщают явное
отключение, если `event_sources` не задан. Сначала обновите сервер, затем агенты: старый сервер
со строгим декодированием не принимает добавленное поле состояния событий.


## Карточки инцидентов и рабочее место ИБ

Раздел «Инциденты ИБ» использует отдельное хранилище `-events-db`. Карточку можно
создать вручную или из срабатывания, указать описание, приоритет и ответственного.
Связанные срабатывания сохраняют объяснение правила и исходные события.
Комментарии, изменения реквизитов, связи и переходы статусов сохраняются с автором,
временем и версией карточки. Удаление связи требует причины и сохраняет доказательства.

Статусы: новый → в работе → локализован / решён → закрыт. Для решения и закрытия
нужны заключение и классификация; повторное открытие требует пояснения.
Закрытая карточка доступна для чтения и повторного открытия. Конкурирующее изменение
возвращает HTTP 409: необходимо обновить карточку перед повтором.

Роль `analyst` («Аналитик ИБ») ведёт расследования и подтверждает срабатывания,
но не меняет агентов, задания, расписания, группы или учётные записи.
Администратор и оператор также ведут карточки; наблюдатель читает их.
Ответственным может быть действующий аналитик, оператор или администратор.
Разделение данных по организациям и подразделениям пока отсутствует.

При первом запуске новая версия автоматически обновляет управляющую SQLite до v11,
а базу событий до v3 с сохранением существующих данных. Перед обновлением сервера
сделайте согласованную резервную копию обеих БД при остановленной службе.

Управляемая установка обновлений доступна отдельным opt-in контуром: именной
администратор выбирает KB/пакеты, получает предварительную проверку на агенте и
подтверждает установку. По каждому обновлению сохраняются результат и необходимость
перезагрузки. Cerber не запускает перезагрузку. Установка не использует обычную очередь
инвентаризации: нужен ключ подписи сервера и отдельный привилегированный исполнитель.
Поддержаны WUA, APT/dpkg и DNF 4; APT-RPM/YUM/DNF5 и сторонние MSI/EXE отклоняются.
Подробности настройки, ограничений и проверки на стенде: [управляемые обновления](deploy/patch/README.md).
Управляющая SQLite обновляется до v11; событийная обновляется до v3.


## Поиск событий, сроки хранения и архивы

В разделе «События и корреляции» поиск выполняется сервером по всему оперативному
журналу, с постраничной выдачей по 100 записей. Поиск по словам/фразе использует
SQLite FTS5 `unicode61`, поддерживает кириллицу и не интерпретирует пользовательский
текст как SQL или язык запросов. Поиск охватывает сообщение, пользователя, IP и
структурированные исходные данные. Это поиск токенов/фразы, не регулярное выражение
или произвольная подстрока; операторы AND/OR и звёздочки не являются командами.

Фильтры: точный ID агента, источник, класс, обработка, пользователь (приводится к
нижнему регистру, как при нормализации), точный IP, код события, результат, период.
Можно выбрать время события либо время приёма сервером. Начало периода включается,
конец исключается; даты веб-формы переводятся из часового пояса браузера в UTC.
События упорядочены по последовательности поступления, а не по часам источника.
Один запрос поиска ограничен пятью секундами; при большом журнале сужайте период/агента.
Срабатывания корреляций показаны отдельным списком и фильтром журнала не ограничиваются.

Для архивов укажите отдельный приватный каталог на сервере:

```sh
./bin/cerber -db .local/siem.db siem serve -admin \
  -events-db /srv/cerber/events.db -event-archive-dir /srv/cerber/event-archives
```

Каталог должен быть абсолютным, доступным на запись только службе/администратору,
отдельным от публично обслуживаемых файлов. Бинарные файлы архива создаются с правами
0600 на Unix; на Windows заранее ограничьте ACL каталога. Корневой каталог не должен
быть symlink. Путь задаётся локально при запуске, через веб-API нельзя задать путь
или имя файла. Перенос существующего каталога требует согласованного переноса всех
пакетов вместе с событийной БД при остановленном сервере.

Откройте «Хранение и архивы». Именной администратор может включить обслуживание,
задать оперативное хранение (1–3650 дней) и хранение архивного пакета после создания
(1–36500 дней; 0 — бессрочно). По умолчанию политика выключена, значения 30/365 дней
не запускают очистку без явного подтверждения. Изменения политики версионируются;
конфликт возвращает HTTP 409. Новая политика действует и для существующих данных.
Аналитик, оператор и наблюдатель могут читать состояние/историю и скачивать архивы,
но не менять сроки или запускать обслуживание. Общий bootstrap-ключ не управляет политикой.

Каждую минуту переносится до 250 подходящих событий. Ручной запуск использует тот же
ограниченный проход и записывает имя инициатора в аудит. Архивируются только события,
у которых время приёма и время события старше оперативного срока и которые прошли
оба потребителя. Необработанный хвост остаётся в БД. Все доказательства срабатываний
сохраняются в оперативной БД независимо от подтверждения срабатывания или закрытия
инцидента; сами срабатывания и история карточек не удаляются этой политикой.

Пакет — gzip с JSONL-строками `ArchiveRecord` v1: серверный ID/последовательность,
агент/актив, время приёма, исходная запись и нормализованная запись с версией парсера.
Перед удалением оперативной копии сервер завершает запись, синхронизирует файл,
повторно читает/проверяет пакет и публикует его. Индекс архива, отпечатки выведенных
событий, удаление исходной/нормализованной записи и FTS, уменьшение учтённого объёма
и запись аудита фиксируются одной транзакцией. Ошибка файла или аудита сохраняет
оперативные записи. Повторная доставка проверяется по отпечатку и не возвращает
событие из архива в оперативный журнал.

Список пакетов содержит SHA-256 и количество записей. При скачивании сервер повторно
проверяет размер и SHA-256; повреждённый файл не выдаётся как исправный. Поиск по
содержимому архивов в веб-интерфейсе пока отсутствует: пакет можно скачать, а исходник
открыть по известному ID. Чтение по ID автоматически обращается к архиву; после
истечения его срока возвращает HTTP 410. Архив — не резервная копия управляющей БД.

Удаление зарегистрированного архивного пакета после срока проходит с сохраняемой
отметкой `expiring`, затем `expired` и аудитом; сбой между удалением файла и записью
итога допускает повторное завершение. Проверка целостности предшествует удалению:
повреждённый/неожиданно отсутствующий активный архив требует разбирательства.
При ошибке БД после публикации файла или аварийном завершении могут остаться
незарегистрированные `.jsonl.gz`/`.pending-*`: они намеренно не удаляются автоматически
и не подпадают под срок зарегистрированных пакетов. Сверьте их с `event_archives`
и оперативными данными перед ручным восстановлением/очисткой. Это ограничение текущего
локального адаптера; полноценного восстановления архива/объектного хранилища нет.

SQLite повторно использует свободные страницы; размер файла автоматически не уменьшается.
Учтённый лимит приёма 1 ГиБ включает исходники и квитанции, но не весь физический объём
БД/FTS/WAL. Квитанции, отпечатки для повторной доставки, метаданные архивов, доказательства
и аудит остаются: политика не обещает ограничить полный размер БД заданным числом дней.
Поздние события за пределами сохранённой оперативной истории не получают автоматическую
повторную корреляцию с архивом. Перед обновлением до событийной схемы v3 остановите сервер
и сохраните согласованную копию БД, WAL и архива; миграция строит индекс существующих событий.
Для этого адаптера используйте один серверный процесс на событийную БД/архивный каталог.


### Сетевые события: межсетевые экраны и FESS WAF

Адаптер `network:cef` принимает CEF:0 как отдельный явно настроенный источник.
Профиль `fess` соответствует экспортёру `rkislov/fess/internal/api/siem_exporter.go`:
`WAF event`, `Proxy access`, `Audit`, время `rt` в RFC3339. Аудит конфигурации
не считается сетевой блокировкой. Профиль `firewall` требует `act`, `src`, `rt`;
для портового сканирования нужны `dst` и `dpt`. Неизвестные действия остаются
неопределёнными; повреждённые записи попадают в карантин. Поля CEF не подтверждают
подлинность производителя — доверие задаётся защищённым каналом и правами файла.

В `event_sources` конфигурации агента можно указать
`journald,cef-fess:/var/lib/cerber-input/fess.cef` либо
`cef-firewall:/var/lib/cerber-input/firewall.cef`. Один CEF-файл на агента.
Локальный syslog-приёмник должен писать завершённые строки в защищённый append-only
файл; при удалённом приёме используйте TLS и проверку отправителя. Cerber не открывает
публичный UDP/syslog-порт. FESS старого CEF-экспортёра отправляет TCP/UDP без TLS и
подтверждения доставки: подключайте его к локальному приёмнику; потери до записи
в файл Cerber восстановить не может. Ротация/усечение требуют согласованной передачи
курсора; при обнаружении изменения префикса или усечения агент останавливает чтение,
сохраняя курсор. Замена файлом с идентичным префиксом не всегда обнаружима.

После записи в файл курсор и пакет сохраняются в штатном долговечном spool агента;
повторная доставка идемпотентна. Можно также отправлять `network:cef` через штатный
аутентифицированный `/v1/agent/events`: `data` содержит `profile` и исходную `line`.
Этот формат не заменяет адаптеры конкретных производителей МЭ: их необходимо
проверить на реальных обезличенных журналах перед включением.

Правила версии 1: `firewall.denied_burst` (20 отказов/5 минут),
`firewall.port_scan` (20 различных портов назначения/5 минут),
`fess.blocked_burst` (10 блокировок/5 минут), `fess.allowed_after_blocks`
(разрешение после 5 блокировок/5 минут). Ключ: агент, профиль, продукт, устройство,
IP источника и назначение; окна не объединяют разные виртуальные хосты FESS.
До 100 последних обработанных отказов, подавление повторов каждого правила и ключа
на 5 минут. Возможны NAT, согласованные сканеры и обычный запрос после блокировки;
срабатывания требуют расследования. Описание, ограничения и исходные доказательства
доступны в штатном интерфейсе срабатываний и карточках инцидентов.

Для HTTPS за доверенным локальным reverse proxy используйте
`siem serve -admin-secure-cookies` и закрытый backend на loopback/изолированной сети.
Флаг включает Secure-cookie и проверку HTTPS Origin; заголовки произвольного клиента
не меняют этот режим. TLS завершает прокси с действительным сертификатом.


Штатный сбор `journald` также распознаёт UFW `[UFW BLOCK]`, `[UFW REJECT]`,
`[UFW ALLOW]` и сообщения с префиксами `CERBER_IPT_DROP ` / `CERBER_NFT_DROP `,
`CERBER_IPT_ACCEPT ` / `CERBER_NFT_ACCEPT `. Только `_TRANSPORT=kernel`;
поля `_HOSTNAME`, `SRC`, `DST`, `DPT` сохраняют устройство и назначение.
Для iptables/nftables администратор должен настроить LOG с этим префиксом вместе
с соответствующим verdict в том же правиле/цепочке: само наличие LOG не доказывает DROP.
Правила firewall применяются и к этим нормализованным событиям. Cerber не меняет
правила МЭ и не включает журналирование автоматически. Агенту нужен доступ к
systemd-journal. Начальное подключение читает последние 100 записей, далее сохраняет
долговечный курсор. Имеющийся поток kernel-журнала и его rate limiting могут ограничить
полноту событий; отсутствие записи не означает отсутствие блокировки.


Локальный приёмник запускается отдельным процессом:

```sh
cerber events receive-cef -listen 127.0.0.1:5514 -file /private/fess.cef
cerber events forward-cef -file /private/fess.cef -profile fess \
  -spool /private/delivery.db -credentials /private/credentials.json \
  -server https://siem.example
```

`receive-cef` принимает только loopback TCP и строки с LF (не octet-count framing),
до 8 соединений, до 15 000 байт строки, таймаут чтения 30 секунд. Каждая завершённая
строка синхронизируется на диск. Файл ограничен 1 GiB: после заполнения приёмник
закрывает соединение; нужна операторская передача/архивация spool без потери курсора.
Автоматического удаления/усечения нет. Legacy-экспортёр FESS не имеет подтверждения
долговечной записи и может потерять данные на обрыве; это не канал exactly-once.
`forward-cef` отправляет штатные пакеты с токеном зарегистрированного агента, сохраняет
повторы в отдельной SQLite БД и публикует здоровье сборщика. Инвентаризацию он
не выполняет; для узла используйте обычный агент. Утраченные до spool данные
не восстанавливаются автоматически. Исходные CEF могут содержать чувствительные URI:
права файла, резервное копирование и сроки хранения выбирает оператор.

### Проверка сетевых кандидатов по пакетам Ubuntu

Сетевые активы связываются с инвентарём только при единственном действующем агенте
с тем же управляемым IP. За NAT и при смене адресов владелец должен проверить это
соответствие. Для Ubuntu/APT агент передаёт исходный пакет и его полную версию
из `dpkg-query`. Сервер загружает официальные записи Canonical Ubuntu OSV только
для обнаруженных CVE и сравнивает версии с учётом Debian epoch, revision и backport.

В карточке показаны результат проверки пакета, версия исправления, снимок агента,
время и SHA-256 источника. История хранит переходы результата, включая исправление
после обновления. Исправленные пакеты исключаются из счётчика активных сетевых
кандидатов; подтверждённое сканером срабатывание сохраняется даже при расхождении
с версией пакета — работающая служба может требовать перезапуска.

Поддержаны явные связи сервисов OpenSSH, Apache, nginx, Dovecot, Postfix, OpenSSL,
Exim с пакетами Ubuntu. Нужны полный инвентарь не старше суток, точный выпуск Ubuntu
и закрытый диапазон исправления OSV. Неизвестный выпуск, ESM/Pro, открытый диапазон,
неоднозначная роль пакета, несколько CVE у одной записи БДУ, недоступный или
устаревший источник дают «недостаточно данных». Отсутствие записи не означает
отсутствие уязвимости. Проверяется установленный пакет, не факт эксплуатации.
Для РЕД ОС и Astra Linux доступен отдельный адаптер OVAL, описанный ниже.
Windows пока сохраняет сетевой статус кандидата.

Источник данных: [Canonical Ubuntu Security Notices](https://github.com/canonical/ubuntu-security-notices),
[описание Ubuntu OSV](https://documentation.ubuntu.com/security/security-updates/osv/).
Данные Canonical имеют отдельную лицензию CC-BY-SA-4.0; код Cerber — Apache-2.0.
Исходные записи не включены в репозиторий, сервер сохраняет их в локальном кэше.

### РЕД ОС и Astra Linux: проверка пакетов по OVAL производителя

Отдельный адаптер использует официальные OVAL-файлы РЕД ОС 7.3 и 8,
Astra Linux 1.7/1.8 для x86_64 и ALT Linux p10/p11. Файл выбирается по точному ID/выпуску ОС и,
для Astra Linux, архитектуре; семейство `ID_LIKE` не служит основанием для
применения исправлений другого дистрибутива. Нужен полный инвентарь не старше суток.

Сервер потоково разбирает XML без выполнения команд/скриптов из источника,
сохраняет нормализованные определения, URL, время производителя/получения и
SHA-256. Кэш обновляется раз в сутки и по кнопке обновления каталога. При ошибке
предыдущий кэш сохраняется, но результат проверки становится неопределённым.
Источники загружаются только для обнаруженных управляемых узлов этих выпусков.

Поддержан ограниченный набор OVAL: явный OR из проверок native package EVR
`less than`, точное имя пакета, `check=all`, `at_least_one_exists` и точная платформа.
Сравнение учитывает Debian EVR либо RPM E:V-R, epoch, числовые сегменты, `~` и `^`.
Для RPM проверяются все параллельно установленные версии. Должен быть найден
пакет, соответствующий роли сетевого сервиса; все упомянутые в определении
установленные пакеты участвуют в оценке. AND, отрицания, расширения определений,
переменные, шаблоны имён и дополнительные условия не упрощаются: такие записи
дают «недостаточно данных». Отсутствующий пакет/запись не доказывает исправление.

В карточке актива видны источник OVAL, идентификаторы определений, полные
установленные версии и границы исправления; история сохраняет изменения статуса.
Это оценка пакетов, а не полная реализация OVAL/OpenSCAP и не проверка эксплуатации.
Другие RPM-дистрибутивы и Windows KB требуют отдельных адаптеров: нельзя
переносить на них границы исправления из РЕД ОС или Astra Linux.

Документация производителей:
[РЕД ОС 8 / OpenSCAP](https://redos.red-soft.ru/base/redos-8_0/8_0-security/8_0-scan-vuln/8_0-openscap/),
[РЕД ОС 7.3 / OpenSCAP](https://redos.red-soft.ru/base/redos-7_3/7_3-security/7_3-scan-vuln/7_3-openscap/),
[файлы Astra Linux](https://dl.astralinux.ru/astra/oval/).
Данные производителей загружаются во время работы и не включаются в поставку кода.


Для ALT Linux официальный источник — [ALT Linux Errata / OVAL p11](https://rdb.altlinux.org/api/errata/export/oval/p11)
и аналогичный endpoint `/p10`. Он возвращает ZIP с отдельными XML, а не один XML.
Сервер читает записи ZIP без распаковки путей на диск, проверяет CRC, пределы размера,
числа файлов и имена; временный ZIP с правами 0600 хранится рядом с БД каталога и
удаляется после обработки. Архив целиком не сохраняется в кэше.

Агент передаёт `CPE_NAME` и `ALT_BRANCH_ID` из `/etc/os-release`. Выбор p10/p11
соответствует явному CPE-условию производителя, включая исключение ALT СП;
при расхождении ветки и CPE результат неопределённый. Одна строка VERSION_ID
не является основанием для выбора ветки. Для ALT отдельно поддержано точное
условие `AND(проверка платформы производителя, OR(пакетные проверки))` и класс
определений `patch`. Произвольные проверки файлов/регулярные выражения не
исполняются. Используется native APT-RPM инвентарь; неопределённая роль сервиса,
нестандартная ветка и спорная для старого RPM семантика `~`/`^` не дают статуса
«исправлен». Для этих полей нужен агент, собранный из текущей версии.

### Защита ёмкости хранилища событий

Политика «Хранение и архивы» независимо задаёт лимит исходников/квитанций,
физический бюджет SQLite + WAL + SHM, бюджет архивного каталога и резерв свободного
места на каждом разделе. По умолчанию физические бюджеты — 16 ГиБ / 8 ГиБ,
резерв — 2 ГиБ. Сроки хранения не сокращаются при заполнении: бессрочные архивы
сохраняются, новые партии остаются в очередях агентов. Сервер возвращает 503 с
`Retry-After` и подтверждает только уже закоммиченные партии. Повтор ранее принятой
партии получает прежнее подтверждение даже при защитной приостановке.

Контроль учитывает размеры файлов, а не только размер JSON исходника: индексы,
нормализованные события и история тоже занимают место. Перед приёмом оставляется
дополнительный запас под обработку; обработчик и архиватор имеют отдельный аварийный
резерв. Если измерение недоступно, приём закрывается до восстановления проверки.
Архивный каталог проверяется также на отдельном разделе; измеряются все файлы,
включая незарегистрированные остатки. Удаление архивов по размеру не выполняется.

Фоновое архивирование переносит до 250 событий / примерно 8 МиБ за партию;
при наличии работы следующая партия начинается через секунду, без работы — через
минуту. Сначала проверяются SHA-256/содержимое и синхронизация файла, затем удаляются
оперативные копии в транзакции. Связанные со срабатываниями доказательства остаются
в оперативной БД. Бюджет ограничивает также размер создаваемого gzip-файла.

SQLite использует ограничение страниц, автоматический checkpoint и ограничение
сохраняемого WAL в 64 МиБ. Обслуживание запрашивает TRUNCATE-checkpoint; если читатель
удерживает WAL, его снимок сохраняется, попытка повторяется позже. Свободные страницы
БД переиспользуются. Полный VACUUM большой действующей БД автоматически не запускается:
он требует дополнительного места и окна обслуживания. Лимит WAL не отменяет
потребность в месте для активной транзакции/длительного читателя.

В дашборде и окне политики показаны физическое использование, повторно используемые
страницы, размещение разделов, резерв, checkpoint и причина приостановки. Пороговые
и защитные состояния создают сохраняемые предупреждения и штатные email-уведомления.

Это защита записей Cerber, а не общесистемная файловая квота: соседняя служба может
расходовать тот же диск. Для устойчивого хранения 7 дней и бессрочного архива нужен
том достаточного размера; локальный SQLite + WAL должен находиться на локальной
файловой системе. Существующие `-events-db` и `-event-archive-dir` позволяют размещать
БД и архивы на разных смонтированных томах. При заполнении бессрочного архива
требуется расширить/перенести хранилище; очереди агентов также конечны.

### Уязвимости Windows: Microsoft MSRC

Карточка агента Windows содержит вкладку «Уязвимости Windows · MSRC» с CVE,
CVSS, продуктом Microsoft, текущей и исправленной сборками, KB и доказательствами
проверки. После управляемой установки обновления запустите новый сбор инвентаря;
проверка читает последний выбранный снимок, ничего не устанавливает и не перезагружает.
На карте сетевого актива MSRC также уточняет найденный CVE, если IP однозначно связан
с аутентифицированным инвентарём Windows. Сетевая находка не подменяется результатом
проверки установленной ОС.

Сервер получает официальный [MSRC CVRF 3.0](https://github.com/microsoft/MSRC-Microsoft-Security-Updates-API)
без API-ключа. Начальный импорт документов с 2016 года идёт по две месячные публикации
за проход с паузой в минуту, начиная с новых. Число загруженных/ожидаемых документов,
ошибки и завершение первичного импорта видны во вкладке и в разделе сканирования сети.
Индекс проверяется раз в час, неизменённые документы — не реже раза в неделю;
администратор может запросить проверку источника. До окончания импорта проверяется
только загруженная часть; пустой результат не означает отсутствие уязвимостей.

В кэше остаются сжатые записи по продукту и месяцу, а не исходные большие документы.
Публикация заменяется транзакционно; неудачное обновление сохраняет прежние записи,
но не выдаёт их за свежую проверку. Размер ответа ограничен 64 МиБ, распаковка одного
продукта — 32 МиБ, сжатые записи каталога — 256 МиБ; перед импортом требуется
свободный резерв 3 ГиБ + 64 МиБ. Это отдельные таблицы существующего каталога,
без изменения событийной и основной схем БД.

Сопоставление требует известной редакции, архитектуры, ветки сборки и полного свежего
инвентаря ОС (до суток). Поддерживаются обычные Windows 10/11 и Windows Server
2012/2012 R2/2016/2019/2022/2025; для Server обязателен тип установки GUI/Core.
Неизвестные редакции, Insider/нестандартные ветки, IoT и приложения Office/SQL Server
не получают автоматического заключения по правилам ОС. Для условно установленного
компонента MSRC подтверждает затронутую сборку продукта, а не возможность эксплуатации.

Исправленные сборки сравниваются только внутри одной ветки. Замены KB используются
только по явно указанным Microsoft связям `Supercedence` для того же продукта и
архитектуры; больший номер KB не означает замену. Отсутствие KB в частичном WUA
не доказывает уязвимость. Если KB установлен, но сборка ниже исправленной, либо
перезагрузка ещё требуется/её состояние неизвестно, результат — «требует проверки».
При неизвестной границе сборки наличие KB само по себе не доказывает активацию исправления.

Новый Windows-агент дополнительно передаёт DisplayVersion, InstallationType и
состояние необходимой перезагрузки из WUA/CBS. Старые снимки принимаются, но могут
не содержать сведений, необходимых для подтверждения исправления. Переустановите
обновлённую службу агента и соберите свежий инвентарь. Реальную установку и проверку
после перезагрузки следует проверять на выделенном Windows-узле.

### Контекст расследования и возможные цепочки

В срабатывании и карточке инцидента доступен раскрываемый блок «Контекст и возможные
цепочки». Он читает согласованный снимок событийной БД и предлагает прямые связи
с опорными срабатываниями: одинаковые аутентифицированные агент/актив и общий ID
исходника, строка пользователя либо корректный IP источника в пределах ±30 минут.
Связи не расширяются транзитивно. Одинаковый IP разных агентов/активов не объединяет
их; loopback, multicast и неопределённые адреса не служат ключом IP. Общие/NAT-адреса
и совпадение имени пользователя требуют проверки аналитиком.

Две версионированные гипотезы для правил v1: успешный вход после отказов, за которым
следует очистка Windows-аудита тем же именем пользователя; разрешённый после
блокировок запрос с совпадением ThreatFox IOC на том же исходном событии.
Это интерпретация известных срабатываний, без автоматического создания инцидента,
изменения приоритета, новых оповещений или запуска active response. ATT&CK и исходники
открываются отдельно. Для Windows 1102 поддерживается настоящий провайдер
[Microsoft-Windows-Eventlog и поля UserData/LogFileCleared](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-1102);
новый агент извлекает инициатора из SubjectUserName/SubjectDomainName, нормализатор
сохраняет происхождение как `windows-audit/2`. Прежний формат принимается, но старые
события автоматически не перепроигрываются.

Для инцидента рассматриваются до 20 последних связанных срабатываний; для каждого
опорного — до 200 соседних кандидатов. В ответе до 100 прямых связей и 20 гипотез,
признак усечения обязателен. Ограничения времени чтения — 5 секунд для событий и
8 секунд для полного контекста, не более двух параллельных запросов. Индекс
`detections(agent_id,event_time,sequence)` добавляется при наличии физического
резерва; его построение не обходит защиту хранилища. Схемы control/events не меняются.

Контекст уязвимостей берётся только для однозначно связанного владельца IP
управляемого актива, совпадающего с агентом и активом опорного срабатывания.
IP атакующего и агент, исполнявший сетевой скан, владельцами цели не считаются.
Используются существующие кэш и сканирования, без новых сетевых проверок/загрузок;
устаревшее наблюдение помечается. Просматриваются до 256 сетевых наблюдений,
до 10 управляемых IP и 20 находок на IP. Наличие CVE не доказывает эксплуатацию.

Аналитик, оператор или администратор может выбрать до 20 предложений и явно связать
их с открытым инцидентом, указав причину. Операция атомарна, защищена версией карточки
и CSRF; любой ошибочный/повторный ID откатывает весь пакет. История хранит автора,
причину и полный список ID. Наблюдатель имеет только чтение. При раскрытом контексте
автообновление страницы приостанавливается, чтобы не сбрасывать выбор и ввод.

### Настраиваемые политики корреляции

Раздел «Правила корреляции» управляет условиями десяти встроенных правил:
отказы входа/успех после отказов, очистка аудита Windows, SYN/блокировки/сканирование
портов МЭ, блокировки/разрешение после блокировок FESS и два типа совпадений ThreatFox.
Это ограниченные типизированные настройки, без выполнения пользовательского кода.

Для пороговых правил: 1–100 событий (для сканирования — различных портов), окно
10–3600 секунд, подавление повторов 0–3600 секунд. У одиночных правил Windows 1102
и IOC порог равен 1, окно/подавление — 0. Исходные условия сохранены версией параметров 1;
без изменений администратором прежние правила продолжают работать. Более специфичный
port_scan имеет приоритет над denied_burst, если его собственные область и порог выполнены.

Область — до 32 групп по ИЛИ; пустой список означает всех агентов. Исключения имеют
приоритет: точные ID агентов, нормализованные имена пользователей (с доменом), IP/CIDR
источника и назначения, до 32 значений на список. Исключается только участие в данном
правиле, а не сбор/хранение события и не другие правила. Для истории окна действуют
те же исключения. Группы разрешаются из основной БД и кэшируются в пределах партии;
если источник нужного состава групп недоступен, транзакция откатывается и курсор
сохраняется для повтора. Архивированные группы не включают агентов.

Администратор с именной учётной записью сохраняет и активирует новую версию,
обязательно указав причину. Контроль ожидаемой версии предотвращает перезапись
параллельных изменений. История неизменяема: откат копирует параметры старой версии
в новую, с новым автором/временем/причиной и ссылкой на восстановленную версию.
Новые таблицы correlation_policy_versions/active добавляются к событийной БД;
control/events user_version остаются 12/5. Срабатывание сохраняет версию реализации
правила 1 отдельно от версии параметров, снимок настроек, совпавшие группы и SHA-256.
«Почему сработало» показывает эти фактические настройки; последующие изменения
не меняют объяснение уже созданного срабатывания. Старые срабатывания остаются
с прежним описанием встроенной версии. Редактирование не переигрывает обработанные
события; ещё не обработанная очередь использует параметры на момент обработки.
Полный новый набор ThreatFox, как и ранее, перепроверяет оперативную историю по
действующей политике IOC; сохранённые ID совпадений не создаются повторно.

Администратор, оператор и аналитик могут проверить черновик до активации. Наблюдатель
имеет только чтение. Выберите события на странице либо укажите до 100 точных ID
нормализованных событий. Тест использует тот же вычислитель и условия приоритета,
историю оперативного журнала до последовательности выбранного события, текущий
состав групп и снимок текущего IOC-набора. Архивы не подмешиваются. Проверка не
создаёт срабатываний/инцидентов, не двигает курсоры, не меняет настройки, не отправляет
почту и не вызывает active response. Подавление моделируется только между выбранными
событиями; существующие боевые срабатывания не подавляют тестовый результат.

Границы теста: до 8 МиБ выбранных событий, история до 100 записей/8 МиБ на окно,
до 200 результатов, 5 секунд чтения БД и не более двух параллельных тестов. Усечение
обозначается явно, а отсутствие результата в ограниченной выборке не доказывает
отсутствие активности. Для IOC нужен загруженный набор; отсутствие набора/удалённого
события возвращается как ошибка, а не как успешная проверка без совпадений.

### Корреляции между узлами

В «Правилах корреляции» доступны четыре дополнительных правила с версиями,
откатом и изолированной проверкой:

- `chain.domain_account_hosts`: сетевые/RDP-входы одной доменной учётной записи
  на трёх различных узлах за 15 минут; ключ — SID из событий Windows 4624.
- `chain.logon_guid_hosts`: одинаковые SID и ненулевой Logon GUID на двух
  узлах за 15 минут. Нулевые GUID не объединяются.
- `chain.ssh_key_hosts`: успешный `Accepted publickey` с одним SHA256-отпечатком
  на трёх узлах за 15 минут. Это общий ключ, а не доказательство единого владельца
  локальных учётных записей. Входы по паролю не объединяются по имени `root`.
- `chain.remote_logon_audit_clear`: вход на другом узле, затем вход на текущем,
  затем Security 1102; одинаковый доменный SID, а на последнем узле — тот же
  локальный Logon ID. Строгий порядок времени, окно 30 минут, минимум два узла.

Порог — 2–20 различных AgentID **и** AssetID. Окно 10–3600 секунд и подавление
0–3600 секунд настраиваются; по умолчанию подавление 15 минут. Оно действует
по общему ключу между узлами. Группы и исключения применяются к каждому
участнику, а не только к последнему узлу. Состав совпавших групп каждого шага
сохраняется вместе с неизменяемым снимком параметров.

В срабатывании, его объяснении, контексте инцидента и результате проверки
доступна последовательность событий: время, узел, учётная запись, SID/сеанс/ключ,
тип и основание каждой связи, кнопки исходников со всех участвующих агентов.
Отображение использует сохранённую цепочку, без произвольного достраивания графа.
Открытая цепочка приостанавливает автоматическое обновление страницы.

Нормализатор `windows-auth/3` извлекает TargetUserSid, TargetDomainName,
TargetLogonId, LogonGuid и LogonType; `windows-audit/3` — SubjectUserSid и
SubjectLogonId. Локальные, встроенные и машинные учётные записи исключены из
межузлового SID-сопоставления. Форматы SID/GUID проверяются. Нужны Computer и
домен из источника; отдельного подтверждения принадлежности SID через AD нет.
Старые агенты, передающие все EventData, совместимы. Для 1102 нужен сбор полей
UserData.LogFileCleared (поддерживается текущим Windows-сборщиком).

Linux использует уже передаваемые journald-сообщения от UID 0 с `_EXE` sshd или
sshd-session. Отпечаток извлекается только из успешного publickey-входа.
`_BOOT_ID` и `_PID` задают локальную SSH-сессию при наличии этих полей.
Одинаковый локальный Logon ID/PID на разных узлах не является межузловой связью.
Windows Logon ID может повториться после перезагрузки; проверьте исходники и
время загрузки перед выводами о причинности.

История ограничена 200 записями / 8 МиБ на выбранное событие, цепочка — 20 узлами
плюс очисткой аудита. Ограничение явно отмечается. Используются частичные индексы
явных идентификаторов в оперативном журнале; архивирование автоматически удаляет
соответствующие индексные записи. Старые события без новых полей автоматически
не обогащаются и не переигрываются; поздние события не пересчитывают старые
срабатывания. Отсутствие цепочки не подтверждает отсутствие активности.

Это последовательность наблюдений, а не доказательство атаки или прямого
перемещения между соседними узлами: возможны штатное администрирование, SSO и
общие ключи автоматизации. ATT&CK-связи условны. Межузловые правила не создают
даже учебные предложения блокировки IP и не запускают active response.
Новые политики хранятся в отдельных таблицах, чтобы возврат к предыдущей сборке
сохранял работоспособность десяти прежних правил; основная версия схемы не меняется.

Семантика Windows-полей: [Microsoft 4624](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4624),
[Microsoft 1102](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-1102).

### Граф цепочки в карточке инцидента

В карточке инцидента откройте **«Открыть граф цепочки между узлами»**.
Граф строится по сохранённым цепочкам явно связанных с инцидентом срабатываний.
Каждый узел имеет свою дорожку, события идут по времени; карточки показывают
учётную запись и переданный идентификатор сеанса. Стрелки сохраняют исходный
тип и основание сопоставления (SID, GUID, SSH-ключ, локальный сеанс).
Совпадение имени или IP не создаёт дополнительных рёбер.

Нажатие на событие раскрывает полный SID, GUID, локальный сеанс, SSH-отпечаток,
AgentID/AssetID и версии параметров исходных срабатываний. Нажатие на стрелку
показывает основания связи и исходники с обоих концов. Доступны масштабирование,
подгонка по ширине, прокрутка и альтернативный список событий. Элементы графа
поддерживают Tab и Enter/Space. Исходники открываются штатным инспектором;
открытый граф приостанавливает автоматическое обновление карточки.

`GET /admin/api/incident-graph?id=<incident-id>` доступен по действующей сессии,
включая роль наблюдателя. Это отдельный read-only запрос, без поиска соседних
срабатываний и обогащения каталогами уязвимостей; он не создаёт оповещений,
инцидентов, действий реагирования или новых связей. Снимок версии карточки и
связанных цепочек читается в одной транзакции (4 секунды, до 20 цепочек / 4 МиБ,
два параллельных запроса вместе с контекстом расследования).

Отображение ограничено 80 событиями, 20 узлами и 200 рёбрами; усечение явно
отмечается. Общие исходные события и одинаковые типизированные рёбра объединяются,
а разные локальные учётные записи с одним SSH-ключом остаются разными учётными
записями. Локальные сеансы ограничены своим агентом и активом. Конфликтующие
снимки одного ID исключаются с предупреждением. Граф не подтверждает причинность
или прямое сетевое перемещение: это средство расследования наблюдаемой цепочки.
